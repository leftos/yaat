# YAAT-1201 snap map: videomap hold bar -> generated hold point

## Answer in brief
The snap belongs inside `GeoJsonParser.BuildLayout` Step 5, in `RunwayCrossingDetector`, as a new input to Parse (like the existing sidecar `standLeadIns` input). The bar's cross-track from the runway centreline is the per-crossing standoff, replacing `rect.HoldShortNm` for that crossing. Three hazards:
1. A moved bar breaks every consumer that tests "bar is at the runway's holding distance" against `rect.HoldShortNm` +-5 ft. These are the exit and landing logic, not only pathfinding (section 3).
2. The videomap is a new Parse input, so it must be pinned in the recording and checkpoint bundle, folded into the precompute key, and fetched by the server (it has no videomap code today) (sections 1, 2, 4).
3. Both the shipped precompute entry and the bundled layout hold the baked layout, so the format and keys need care (section 4).

## 3. Where the snap sits and what must stay consistent
Seat: `ProcessBoundaryEdge` (`RunwayCrossingDetector.cs:178-254`) decides per boundary edge by the cross-track `rect.HoldShortNm`: (a) reuse a node within 5 ft (`HoldShortSnapFt` :29, :198-206, upgrades `offNode.Type`/`RunwayId`), (b) `FindHoldShortInsertionPoint` walk (:589-684) -> `InterpolateAndInsert` (:693-760), (c) interpolate and `SplitEdgeAtOneNode` (:231-243; `SplitEdgeAtOneNode` :1127), (d) `DeadEndFallback` (:793-). `rect.HoldShortNm` is read at :191,:208,:225,:611,:709,:802,:1056. The clean change is a per-crossing ideal (nm) passed instead of `rect.HoldShortNm` in those sites: the bar's cross-track at its intersection with the taxiway edge polyline (the painted bar is not necessarily parallel to the centreline; a node on a taxiway centreline is the intersection of the bar line with the edge, so compute the fraction along the edge from the bar segment intersection rather than a pure cross-track, if the bar is skewed). Pairing: same runway (cross-track side) and taxiway edge within ~200 ft per the ruling. Candidate videomap bar filter `#fce028` / thickness 2 / zIndex 3 / 2 points / 28-121 ft is OAK data (earlier map :16); nothing flags a bar in the data, so the filter is per airport and unvalidated elsewhere.
Because the walk and reuse tests also use the standoff, a snapped bar nearer than the old ideal that lies on the boundary edge needs the crossOff < ideal branch re-evaluated per crossing; a bar farther than the walk cap (`HoldShortWalkMaxHops` 8) or the dead-end fallback keeps the synthetic bar (record "unmatched").
A hold-short `GroundNode` carries only `Id, Position, Type, Name, RunwayId, Origin` (`AirportGroundLayout.cs:20-72`); there is NO stored standoff, heading or bar line. Everything else is derived from geometry: edges (the split of the taxiway edge via `SplitEdgeAtOneNode`; moving a node's position after the split would leave edge `DistanceNm`/`IntermediatePoints` stale, so place the node at its final position BEFORE the split, which the per-crossing ideal does), adjacency (rebuilt at :428), `ConnectOnRunwayNodes` (:262, sorts by along-track and links the centreline), `coordIndex` (:241, snap tolerance ~10 ft; two bars within 10 ft would merge), and the later fillet merge (coincident-node threshold 5 ft, docs hold-short-placement.md:52-55).
The distance consumers key on `rect.HoldShortNm` from the runway, not on the node, so a snapped bar at a different cross-track breaks them:
- `AirportGroundLayout.IsAtHoldingDistance` (:2717-2718): `cross >= HoldShortNm - 5 ft` -> `ResolveShortBar` (:2579-2595: a bar inside is only an exit when the controller named it, uninstructed exits are rejected), `HopToJoiningBar` (:2604-2611), `IsAtRunwayHoldingDistance` (:2714) used by `LandingPhase.cs:2016,2073`, `RunwayExitPhase.cs:1509`, `HoldingAfterExitPhase.cs:115`.
- The outward walk: `BuildOutwardWalk` (:2703) `HoldingFt`, `TryOutwardStep` (:2813 `nextFt > HoldingFt + 5` rejects a farther bar; :2858 target test). A snapped bar >5 ft beyond the runway's ideal is unreachable as a target; <5 ft inside reads as a short fallback bar.
- `RunwayCrossingDetector.ClassifyRouteNode` (:1047-1070) and `DropRedundantFallbackBars` (:894), which judge fallback bars against `rect.HoldShortNm`.
- `OccupiedRunwayGoAround.cs:187` reads `GroundRunway.HoldShortDistanceFt` for the hold line; `HoldLineFootprint` + `RunwayHoldBars.IsInsideBarLine` use bar positions (HoldLineFootprint.cs:23-35; `RunwayHoldBars.cs`); `RunwayOccupancy` (10 refs).
So the design choice: (a) store a per-bar standoff on the node (new serialized `GroundNode` field -> layout JSON format change -> bump `RecordingArchive.CurrentLayoutFormatVersion`, which makes every older bundled layout "unread, pinned live", see RoomResourcePin.cs:373-376 and `PrecomputeKey` mismatch) and make all of the above read it; or (b) feed the same snapped distance back through `GroundRunway.HoldShortDistanceFt` per runway (single value per runway; fails when the 3 OAK values differ by taxiway; not viable for per-crossing snaps).
Route-level consumers of hold-short position: they read node positions and edges, so a moved node moves them automatically: `HoldShortAnnotator.ComputeHoldShortPositions` (8 refs; stops measured along the route to the painted stop, hold-short-placement.md:100-103), `TaxiRoute`/`HoldShortSetbackNm`, `VirtualNode`, `SegmentExpander` (9), `RouteMaterialiser` (7), `RouteCostFunction`, `TaxiPathfinder`, `RampLaneReposition`, `TugPathCheck/TugMovePlanner/TugLayoutIndex`, `TaxiingPhase` (3), `HoldingShortPhase`, `GroundNavigator` (2), `FollowingPhase` (5), `FollowRoutePlanner`, `GroundCommandHandler` (7+2), `RunwayOccupancy` (10), `OccupiedRunwayGoAround` (4), `SituationFlagCalculator`, `PavementClassifier`, `MovementAreaClassification`, `ExitCapacityResolver`, `FilletPlanCutRedirect`, `TaxiwayWalk` (counts of `GroundNodeType.RunwayHoldShort|RunwayHoldBars.` refs by file from grep in src; 37 files). Client: `GroundViewModel` (8), `GroundRenderer` (bars), `DtoConverter`. Pathfinding sensitivity from a moved split: hold-short-placement.md:219-227 ("Moving a bar moves the graph", node ids renumber, timing-sensitive recordings can desync).
ASDE-X bars (`src/Yaat.Sim/Asdex/AsdexHoldBarBuilder.cs`): only reads the hold node as the lateral side + taxiway name and walks the graph to the runway-edge crossing (`TaxiwayBar` :196-231, `NextEdgeTowardRunway` :255, `TaxiwayName` :301); the drawn bar lies AT THE RUNWAY EDGE (half width), parallel to the runway, independent of the standoff. ## 4. Determinism and replay
Today's treatment of the airport GeoJSON: the layout is PINNED per room (`PinnedAirportGroundData` RoomResourcePin.cs:94-170: layout and source GeoJSON read once from one cache entry, refresh cannot swap them, :260-272), and a recording/checkpoint bundles the BAKED layout (`RecordingLayoutBundler.cs:21-24` `WriteLayout`) plus the source GeoJSON; replay seeds `FromBundle` (:140-170) and runs on the recorded graph (class doc :280-285); a changed live map only logs `replaying the recorded layout; the live map has changed since` (:217-243). Older formats/archives lacking a layout fall back to live (`LogPinnedLive` :180-210, `UnreadFaaCodes`). Test guard: `RecordingArchiveLayoutGuardTests`, `RecordingGroundData.Evergreen/VersionPinned` (tests/CLAUDE.md; 155 uses over 110 test files incl. 27 in `RecordingGroundDataTests`).
Consequence for the videomap: if the snap is applied at Parse and the resulting layout is bundled, an upstream videomap change AFTER recording does NOT change the replay (the baked node positions replay), exactly as for the GeoJSON. Risks: (1) archives with a layout but where replay re-parses the bundled GeoJSON (`BundledLayout.SourceGeoJson` is only used for the changed-map log; the layout is read, not re-parsed; not checked beyond RoomResourcePin) - confirm nothing re-parses the bundled GeoJSON, since the videomap would then be absent/different; (2) the live cache comparison `previous.SourceGeoJson == geoJson` (AirportGroundDataService.cs:206) and the `LogIfLiveMapChanged` compare only the airport GeoJSON, so a videomap-only change would neither re-parse the live layout nor log; add the videomap text/hash to the cache entry; (3) the videomap download failing at room start (offline server) would build an un-snapped layout that is pinned into the room and the recording: make the fetch outcome part of `LayoutFetchOutcome` and cache the last good copy; (4) two rooms starting minutes apart could pin different snaps if the videomap changed in between (acceptable per-room pin, same as GeoJSON); (5) a layout-format bump (needed only if a node field is added) invalidates every old bundled layout (they are re-pinned from live, i.e. replays of old recordings run on the NEW graph unless the bundle is read), so prefer no format bump or a bump decision with `VersionPinned` recordings reviewed. Prefer computing the snap from a committed, hashed sidecar for determinism of tests and CI (TestAirportGroundData reads only `TestData/*.geojson`; a network fetch in tests is not allowed by the repo's real-data rule, so a `TestData/<ID>.videomap.geojson` fixture plus `tools/refresh-test-layouts.py` support would be needed).
Fixed-seed note: Parse is pure on its inputs (node ids by mint order, footgun hold-short-placement.md:214-218); snap must keep a stable order (iterate videomap bars sorted, match deterministically, tie-break by distance then index) so the same inputs give the same ids.
