# YAAT-1201 map: MAP vs GND hold-short bars

## Answer in brief
"MAP" and "GND" are two toggle buttons in ONE view, the Ground View (not `Views/Map/`, which is only the shared canvas base). Toolbar: SAT / MAP / GND (`src/Yaat.Client/Views/Ground/GroundView.axaml:62-82`; tooltips "satellite background image", "video map overlay", "YAAT ground layout"). The satellite toggle belongs to the same view. MAP = tower-cab videomap GeoJSON (`ShowVideoMapOverlay`); GND = YAAT's generated layout (`ShowYaatLayout`). Both can be on at once, which is why the user saw two bars.
The videomap file carries NO hold-short marker: the parser reads only color/thickness, and in the cached OAK file a hold-short bar is a plain 2-point yellow LineString. A fix therefore needs a heuristic to find them, or a rule that ignores them.

## 1. MAP path (videomap)
- Trigger: `GroundViewModel.ApplyScenarioBootstrap` fires `LoadLayoutAsync` and `LoadTowerCabLayersAsync` unawaited and concurrently (`ViewModels/GroundViewModel.cs:665-677`); also `MainViewModel.Timeline.cs:963,973`, `MainViewModel.ViewInstances.cs:422-431` (extra windows: mirror or own load).
- Map id: `ArtccAirportResolver.GetTowerCabVideoMapIdAsync` finds `facility.towerCabConfiguration.videoMapId` in the ARTCC config for the airport id (`Services/ArtccAirportResolver.cs:64-79,158-185`).
- Download/cache: `GroundViewModel.DownloadAndParseTowerCabMapAsync` (`GroundViewModel.cs:471-481`): URL `{VnasConfig.VideoMapBaseUrl}/{artcc}/{videoMapId}.geojson`; cache `%LOCALAPPDATA%/yaat/cache/towercab-maps/{ARTCC}/{videoMapId}.geojson` via `HttpFileCache.GetOrRefreshAsync(HeadLastModified)`. Base url from `VnasConfigService.cs:64`. The satellite image is separate (`TowerCabImageService`, `GroundViewModel.cs:411-431`).
- Parse: `Services/TowerCabMapParser.cs:41-128`. Types: Polygon/MultiPolygon (outer ring only, filled) and LineString/MultiLineString. Properties read: `isDefaults` (default feature, :189-202), `color` (:204-224), `thickness` (:226-239). `zIndex` is IGNORED. Output `TowerCabMapData{Polygons, Lines}` (`TowerCabPolygon`, `TowerCabLine{Points,Color,Thickness}`, :11-28): no feature id, no name, no kind.
- Draw: `GroundRenderer.Render` layer 2 (`Views/Ground/GroundRenderer.cs:730-734`) -> `DrawVideoMapOverlay` (:925-985): all polygons, then all lines, as strokes with alpha = overlay brightness. Order is list order, not zIndex. Objects are immutable-by-convention and handed to the render thread through `GroundCanvas.RenderSnapshot` (`GroundCanvas.cs:920-926,1003`); mirrors copy the reference (`GroundViewModel.cs:768`).
- Cached file found (read-only): `%LOCALAPPDATA%/yaat/cache/towercab-maps/ZOA/01H82AAXSS1HR7R8HHJ6PP6HS3.geojson` (OAK area, lat 37.70-37.74; 1144 features: 386 Polygon, 529 LineString, 229 MultiLineString). Property keys in the whole file: `color`, `thickness`, `zIndex` only. No hold-short property, no name.
  - Candidate hold-short bars (inference, not flagged in data): 35 LineStrings, `color #fce028`, `thickness 2`, `zIndex 3`, exactly 2 points, 28-120 ft long. Other 2-point lines: 349 `#a29857` thk1 z2 short (~10-20 ft, dashes), 59 `#848484` long, 2 `#ffffff` thk2 z3 (maybe other markings). - Runways: on MAP (or GND) YAAT's own `DrawRunways` is drawn from the layout over the videomap (`GroundRenderer.cs:743-753`). So MAP is already a hybrid.

## 2. GND path (generated bars)
- Source: server `TrainingHub.GetAirportGroundLayout` (`yaat-server/src/Yaat.Server/Hubs/TrainingHub.cs:2553-2562`) -> `DtoConverter.ToGroundLayoutDto` (`yaat-server/.../Simulation/DtoConverter.cs:1997-2077`) -> client `ServerConnection.GetAirportGroundLayoutAsync` -> `GroundLayoutDto` (`Yaat.Client.Core/Services/ServerConnection.cs:1956-1998`).
- Each bar = a `GroundNodeDto(Id, Latitude, Longitude, Type=="RunwayHoldShort", Name, Heading, RunwayId)` (`ServerConnection.cs:1965`). Position and combined RunwayId (e.g. "10R/28L") are on the node. The protected taxiway is NOT a field: derived from adjacent non-runway edges' `TaxiwayName` (`GroundRenderer.cs:1815-1825`, `ResolveNearbyTaxiwayNames`). No bar heading/line segment on the wire (docs/ground/hold-short-placement.md:16-19).
- Builder: `RunwayCrossingDetector.DetectRunwayCrossings` inside `GeoJsonParser.Parse` (`Yaat.Sim/Data/Airport/RunwayCrossingDetector.cs:134,154`; standoff = runway `holdShortDistance` ft from centerline, else `HoldShortDistanceForWidth`), then fillets, `DropRedundantFallbackBars`. The source airport GeoJSON has only parking/spot/taxiway/runway features (verified in cached `airports/OAK.geojson`: 168 parking, 34 taxiway, 16 spot, 4 runway) so bars are fully synthetic.
- Draw: `DrawNodes` (`GroundRenderer.cs:1792-1856`) only inside the `showYaatLayout` block (:762-784); `Type=="RunwayHoldShort"` -> `DrawHoldShortBar` (:2140-2151): a +/-30 ft tick, 1.5 ft stroke, perpendicular to the angle from the node to a neighbour node over a non-runway edge (`ComputeHoldShortAngle`, :2090-2126; last edge visited wins, so with two taxiway neighbours the drawn angle depends on edge order). So the angle the user compares is an artefact of node->neighbour direction, not of a stored heading. `GroundFilterMode` `showHoldShort` can hide them (:1805,1853).
- Reachability from MAP code: yes. Same `GroundViewModel` holds both `Layout` (DTO) and `_domainLayout`/`DomainLayout` (`AirportGroundLayout`, `GroundViewModel.cs:69-76,609-610`) and `TowerCabMap`; same renderer, same snapshot (`GroundCanvas.cs:893-926,1003`). Mirror windows copy all three (:758-771). Domain side has `RunwayHoldBars` index (docs architecture.md:2000), `GroundNode.RunwayId/TrueHeading` (`AirportGroundLayout.cs:33,48`). No server round-trip needed; no thread issue if the work is done on the UI thread before building the snapshot (or in the VM when both are loaded). Airports with no layout: `Layout`/`_domainLayout` are null (`GroundViewModel.cs:595-604`); `Render` returns right after the videomap if `layout is null` (:736).
- Load order race: layout and videomap load concurrently and independently (see :671-675); any merge must run when both are present and on either's change (cf. mirror's PropertyChanged handling :738-756).

## 3. Matching and options
Nothing links a videomap bar to a generated one: no shared id, runway or taxiway on the videomap side, and none of its properties identify a bar. Possible join: geometric (nearest generated bar node within N ft AND videomap line roughly perpendicular to a nearby taxiway, near the same side of the runway).
Options:
A. Replace: drop heuristically-identified videomap bars at parse time (new rule in `TowerCabMapParser` or a post-pass), draw generated bars on MAP. Touches `TowerCabMapParser.cs`, `GroundRenderer.cs` (add a bars-only draw when `showVideoMapOverlay && !showYaatLayout`, gated like :743), `GroundCanvas` snapshot unchanged (data already in `Layout`). Failure: heuristic misidentifies other yellow/white markings (the 2 white thk2 z3 lines), per-airport colors differ, the map shows no bars at an airport whose bars are not recognised (then paint bars remain = today's behaviour, safe fallback), and airport with no layout loses bars (drop only when layout present).
B. Move matched bars: after both loaded, for each identified videomap bar find nearest generated node; translate/rotate the line to node +/- its half length, angle from neighbour edge. Touches the same plus a VM merge step and a new immutable `TowerCabMapData` copy (the instance is referenced by an in-flight render snapshot; never mutate in place, `GroundViewModel.cs:693-697`). Failure: unmatched videomap bar stays where painted (still disagrees), one videomap ladder with several lines vs one node, generated bar with no videomap counterpart stays absent, tie-breaks at close parallel bars (OAK 15/33).
C. Hide videomap bars, draw generated bars on MAP: same as A but done at draw time (filter list in `DrawVideoMapOverlay`) so the toggles remain independent; works when MAP+GND both on (then GND already draws bars; hide the paint ones). Failure same as A; extra: MAP+GND both on must not double-draw generated bars.
D. Leave paint, label the discrepancy / setting "MAP bars: videomap | YAAT": a pref beside `GroundShowVideoMapOverlay` (`Yaat.Client.Core/Services/UserPreferences.cs`, `GroundSection.axaml`, SettingsSearchCatalog, SettingsViewModel).
E. (cheaper, code-suggested) Draw generated bars always on MAP and just thin/hide none: shows two bars (current symptom plus one) - not recommended.
Tests: none exist for `TowerCabMapParser`/`DrawVideoMapOverlay`/`TowerCabMap` (searched tests/, only GroundRenderer*Tests for other overlays); pattern to follow: `tests/Yaat.Client.Tests/Views/GroundRendererRouteDrawTests.cs`, `GroundViewModelClearLayoutTests.cs`. Use the cached real OAK videomap as a fixture only if committed under tests (currently not).
Docs to update: `docs/ground-rendering.md` (Render order layer 2/4), `docs/architecture.md` (TowerCabMapParser line 948), `docs/ground/hold-short-placement.md` (says bars drawn by `GroundRenderer.DrawHoldShortBar`), USER_GUIDE.md if user-facing, `CHANGELOG`.

## 4. Who draws the videomap
Only the YAAT desktop client draws this file via the Ground View MAP toggle. yaat-server does not download or serve tower-cab videomap GeoJSON: it only exposes video-map metadata (`ArtccConfigService.VideoMaps.cs:13-130`, `TrainingHub.cs:2565-2568`) and the layout (above); `rg` found no server consumer of the `VideoMapBaseUrl` or the `.geojson` map files (server hits for "TowerCab" are TowerCab 3D aircraft/rooms). CRC Tower Cab fetches the file itself from vNAS (its own source; not read here, CRC decompile not consulted). A client-only edit changes only YAAT's Ground View; CRC's picture is untouched (the cached file is vNAS-authored, read only).
