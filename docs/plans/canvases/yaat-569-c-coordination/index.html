Initiate handoff and Point out flyouts

The aircraft menu's Track › Initiate handoff… and Track › Point out… open today's bare input popup, “Position ID”, and send HO or PO with whatever was typed (MenuCatalog.cs lines 79–93, BuildInput). The instructor has to know that Oakland Tower is 3O and Center sector 44 is C44; nothing lists who is staffed.

The page draws the flyout three ways (lanes A, B, C). Each lane shows four states: Initiate handoff as it opens, the box filtered by oak, a typed code that matches no staffed position (3S), and Point out, which shares the layout. Every box is live: type in it, press Enter, or click a row or chip; the line under the lane says what would be sent.

The situation: scenario S3-NCTC-3 | Area C Complete (docs/atctrainer-scenario-examples/01J02M96SPYP4JV55R5RMVCQBS.json). The student works 3Y, OAK_APP, NorCal Area C Combined, and the scenario connects 19 ATC positions. The aircraft is KFB7, a CL60 from KVNY to KOAK on the EMZOH4, owned by 3Y. Positions, TCPs and frequencies come from docs/vnas-artcc-config-examples/zoa.json.

Carried from parts X5 and B (drawn as given, not as lanes)

  • Every quick command gets a designed flyout; single-box inputs become inline boxes. The “Position ID” popup becomes the box at the top of the flyout.
  • The keyboard model of part B. Focus lands in the box; typing filters; the first match is outlined and Enter sends it, else the typed text upper-cased, as today. Down moves into the rows, Up from the first row returns to the box, and Escape closes the flyout.
  • Screen edge and width (X2b ruling 5): FlipX | SlideY, no shrinking of lists, the 480 px cap. Every flyout here is 380 px wide.

What the client knows about positions (static reads, not run)

  • A list exists, but the menu cannot reach it. MainViewModel.OnlineControllers (MainViewModel.Controllers.cs:55) holds one OnlineControllerDto per staffed position (ServerConnection.cs:1879): Callsign, Name, Frequency, FacilityId, FacilityName, PositionType, Tcp, RadioName, RealName, IsActive, IsScenarioPosition. The server fills it with the room's live CRC clients and the scenario's auto-connect ATC positions (OnlineControllerService). The Controllers tab draws it grouped by facility. IMenuHost has no member that hands it to a menu: needs a host member, no new server data.
  • No row argument for every position. OnlineControllerDto.Tcp is set only from a STARS TCP (ArtccConfigService.BuildOnlineControllerDto). It is null for the ERAM sector OAK_44_CTR (whose argument is C44) and for MER_TWR, which has no TCP; for both, HandoffId falls back to the facility id, ZOA or MER, and HO ZOA names no position. Travis's SUU_S_APP is 1S, the same code as NCT's Seca (MRY_APP). The server already computes the shortest code that names exactly one position, for AS (RoomEngine.SelectionCodeFor: TCP or C+sector, else callsign, else callsign@code). needs new data: that code on each OnlineControllerDto.
  • Unstaffed positions are not listed. HO 3S (Area C Sunol, not staffed in this scenario) resolves from the ARTCC config on the server (TrackResolver.ResolveTcpToOwner). The client's only config list, ScenarioPositionDto (ServerConnection.cs:1742), carries Id, Callsign and Name only: no TCP, no frequency, no facility. Naming 3S in the flyout, or refusing a code that names nothing, needs new data.
  • No “next sector” anywhere. The aircraft carries Owner, OwnerSectorCode, HandoffPeer, HandoffPeerSectorCode and PointoutStatus (IMenuAircraft.cs:200–218), its Destination and its NavigationRoute; nothing on the client or the hub says which sector the route enters next, and no field names the position that handed the aircraft over. The destination's tower is derivable (Destination KOAK against an online FacilityId OAK). Anything else in lane B's Likely group needs new data.
  • Glyphs. Initiate handoff has a strip glyph (QuickCommandGlyphs.cs:181, scope grey). Point out has none; the page draws a dashed draft.
