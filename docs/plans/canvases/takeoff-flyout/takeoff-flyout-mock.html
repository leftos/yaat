Cleared for takeoff flyout

Mock for YAAT-522, in the style of the pattern-entry flyout (YAAT-521). The flyout opens from the Cleared for takeoff strip button and lists different rows for VFR and IFR aircraft. Each row shows the exact command it sends. Type in the boxes and the commands update. Glyphs are drawn for a runway landing and departing west (heading 270), off the runway rectangle.

Open questions

  1. Initial altitude on a plain VFR takeoff clearance needs new grammar. Today CTO 4500 is rejected (a bare number above 360 is not understood) and CTO 045 means fly heading 045. The mock shows CTO 4500, read as an altitude because it is above 360. The other options are a keyword (CTO ALT 4500), or no new grammar: send CTO MSO 4500. That flies the same path for a VFR aircraft, but the readback adds "fly runway heading".
  2. Closed traffic and the altitude box. On CTO MLT/MRT the altitude slot is the pattern altitude (CTO MLT 045 = pattern at 4,500), and the handler ignores a takeoff altitude there. The mock leaves the altitude off those two rows. Alternatives: send it as the pattern altitude, or hide the box when only closed traffic applies.
  3. Pre-filled VFR/045: send it, or only show it? With no altitude in the clearance a VFR departure already climbs to its filed altitude, pattern exits included. Sending 4500 changes only the readback ("climb and maintain 4,500") and stores it as the assigned altitude. The mock sends whatever the box holds. The alternative is to send it only once the controller edits the box.
  4. Inline boxes are a new menu pattern. Today the strip flyout is a plain menu, and free text opens a popup (Custom…). This mock puts a text box inside the flyout: one shared altitude box at the top, and a fix box on each direct row. Still to settle:
    • Does Enter in a fix box send that row?
    • Is a row with an empty fix disabled, as the mock shows?
    • Should the fix box offer route fixes and autocomplete, as Direct to… does?
  5. Which VFR departures, and their wording (for the aviation review, 7110.65 3-9-9, AIM 4-3-2 / 4-3-3). The set chosen here is: make left / right closed traffic; straight out; left / right crosswind departure; left / right downwind departure; on course; turn left / right direct {fix}. Left out:
    • left / right 270 (ML270/MR270) and other relative turns (MR45);
    • plain direct (CTO DCT {fix});
    • cross-runway closed traffic (CTO MLT 33).
  6. "360 overhead" is broken today. The current flyout's "360 overhead" item sends CTO 360, which the sim reads as fly heading 360, and the sim has no overhead departure at all. The mock drops it.
  7. The IFR rows. The request names a plain takeoff clearance and one with a heading. Today IFR also gets Fly runway heading (CTO RH), which tower issues routinely; keep it? Other choices for the heading row:
    • send CTO 270 (shown) or CTO H270;
    • offer turn-direction variants (RT270/LT270);
    • add an altitude box for IFR as well.
  8. An IFR aircraft under "VFR commands for IFR aircraft: All". Today it gets the VFR departures as well. Should the IFR flyout keep adding the VFR rows?
  9. All Commands › Tower › Cleared for takeoff is built by the same code as the strip flyout. Should both change, or only the strip? And should Custom… stay at the bottom?
  10. Glyph rotation and colour. Should the departure glyphs turn to the departure runway, as YAAT-456 does for pattern entries? The strip button keeps today's takeoff glyph. Colour: amber for every row, or purple for the circuit rows (shown)?
  11. The menu needs the filed altitude. The client knows the filed altitude, but the menu's view of an aircraft does not expose it. Showing the pre-filled value needs that added.
  12. Docs follow any new grammar: COMMANDS.md (the quick reference and the modifier table), the command cheat sheet, and USER_GUIDE.md.
