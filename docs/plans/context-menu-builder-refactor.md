# Context-menu builder refactor

> **Decision record.** User steer, 2026-10-02: "The context menus shouldn't vary depending on the view. The context menu builder should just need a callsign and maybe some context about whether another aircraft or a taxi node was clicked, but it should be logic independent from the radar / ground / aircraft list views, and the same options should be offered across all three. We need a context menu builder refactor." It replaces briefs 7e-3 and 7e-4 of [context-menu-quick-commands.md](./context-menu-quick-commands.md) on `feat/context-menu-quick-commands`; step 3 (per-situation quick lists) follows it. Line references are to the feature branch at c8d9b1f4.

Terms used here: **view section**, the few canvas-only items a view appends to the shared menu; **click context**, what the view tells the builder about the click; **point menu**, the menu a right-click on the map or a taxi node opens for the selected aircraft. Each needs a `CONTEXT.md` entry in the commit of brief 1.

## Goal

One view-independent builder in `Yaat.Client.Core` makes the identical aircraft menu on the radar, the ground view and the aircraft list from the aircraft, a click context and one host. Each view adds only its view section of canvas items (Display, Measure, route drawing), so no `MenuView`, host capability flag or per-view builder is left.

## Design

- **Builder.** `src/Yaat.Client.Core/ContextMenus/AircraftMenuBuilder.cs`: `public static ContextMenu Build(IMenuAircraft? aircraft, MenuClick click, IMenuHost host, Func<MenuContext, IReadOnlyList<Control>> viewSection)`. It takes no view; a view's only inputs are the click, the host's anchor and its section.
- **Click context** (`src/Yaat.Client.Core/ContextMenus/MenuClick.cs`): `public sealed record MenuClick(string Callsign, IMenuAircraft? PreviousSelection, MenuPoint? Point, IReadOnlyList<IMenuAircraft> Selection)` and `public sealed record MenuPoint(LatLon Position, int? GroundNodeId, string? RunwayEnd)`. `Callsign` is the aircraft the menu commands (the right-clicked one; on a point click, the selected one). `PreviousSelection` is the sender of the relative items. `Point` is null on an aircraft click, a map position on the radar, a taxi node on the ground (`RunwayEnd` set from a threshold click). `Selection` is the multi-selection: the list's selected rows, `[]` on the canvases.
- **Context.** `MenuContext` becomes `(MenuClick Click, string Initials, bool SoloTrainingMode, VfrCommandsForIfr VfrCommandsForIfr)` with read-through `Callsign` and `PreviousSelection`, so the predicates keep their reads. The builder makes it from the click and `host.Session`; `View` goes.
- **One host interface, one implementation.** `IMenuHost` keeps only what every view serves, and `src/Yaat.Client/Views/ClientMenuHost.cs` `(MainViewModel main, AircraftModel? aircraft, Control anchor)` implements all of it, built per right-click by every view with the control the menu opened on:
  - send: `SendAsync` → `MainViewModel.SendCommandForViewAsync` (made public), so a failed send is caught and shown on every view;
  - session: `Session` → `MenuSession(Initials, SoloTrainingMode, VfrCommandsForIfr)` from `main`; a view that finds no `MainViewModel` logs it and opens no menu, so no fallback mode is needed;
  - popups and pickers: `ShowInputPopup`, `ShowListPopup`, `ShowFilteredListPopup`, `ShowWarpPopup`, `ShowCommandFlyout`, `ShowNoteFlyout` → one popup service, `src/Yaat.Client/Views/MenuPopups.cs`, code-built like `TextEntryPopup` with `PlacementMode.Pointer` on the anchor, so every popup opens at the pointer on every view; `InputFlyout` folds into it;
  - flight-plan editor: `OpenFlightPlanEditor(callsign)` → `FlightPlanEditorManager.Open`;
  - favorites: `BuildFavorites` → `FavoritesContextMenu.Build(main, …)`;
  - RPO items: `BuildRpoItems(IReadOnlyList<string> callsigns)` → `main.BuildRpoMenuItems`;
  - data queries: `FixNames` (`NavigationDatabase.Instance.AllFixNames`), `GetFieldElevation` (navdata elevation of the destination, else the scenario's primary airport), `GetGroundTrafficCallsigns` (`main.Aircraft`), the hold-short, pushback face, push-back-to and preset choices over `main.Ground` (the primary ground view model owns the layout and the other ground windows mirror it, MainViewModel.cs:2190), `SetRoutePreview` on every ground view model (`main.AllGroundViews`), so the hover preview shows on whichever ground window is open, and for the point menu `DescribePoint(LatLon)` (the FRD) and `GetTaxiChoices(callsign, nodeId, runwayEnd)` (today's route variants as a choice tree);
  - `AssumeSelectedLiveTrafficAsync`;
  - no `Capabilities` and no member that throws; the test `RecordingMenuHost` stays the second implementation.
- **The tree**, one order on every view; `ContextMenuProfileService` order and phase hiding stay until step 3, and the service moves to Core with `MenuGroup` and `ContextMenuProfile` (it has no client dependency) so the builder calls it itself:
  1. header: title; route summary and hold status rows, built in Core from new `IMenuAircraft` reads (`NavigationRoute`, `HoldKind`, `HoldYieldTarget`, `AutoYieldTarget`, `AutoYieldIsFollowing`); Release (HFR); Check release window; separator; Command…; Note…; separator;
  2. Favorites, separator;
  3. a delayed spawn (new `IMenuAircraft.IsDelayed`): Spawn now, Change spawn delay, Delete, and nothing else — no view section, no RPO items, as the list's menu today;
  4. an assumable shadow: Assume control, Assume and track, separator; a surface shadow: Track, Data Block, Coordination, then straight to the view section and the foot, nothing that commands it;
  5. the relative items (`AddRelative`);
  6. the ground-movement block, each by its predicate: Push back, the face items, Push back to…, Hold position, Hold short of…, Follow…, Give way to…, Break conflict, Resume taxi, Cross {rwy};
  7. the profile groups (Heading, Altitude, Speed, Navigation, Hold, Approach, Procedures, Tower ▸, Pattern ▸), primary, separator, secondary; an empty submenu is omitted;
  8. Preset taxi route;
  9. separator, Track, Data Block, Squawk, Ask pilot (`CanAskPilot`), Coordination, separator, Edit flight plan (`CanEditFlightPlan`);
  10. the view section, after a separator when it is non-empty (slot: Q1);
  11. the foot: separator, Warp…, Release to live feed, Delete;
  12. "Assume selected live traffic (N)" when `click.Selection` holds two or more assumable shadows;
  13. the RPO items for the selection's callsigns, else `[Callsign]`.
- **Pickers on every view.** Initiate handoff…, Point out…, Squawk…, Ask pilot Custom…, Cleared for takeoff Custom… and every flight picker are built wherever their predicate holds, since every view has the popups.
- **View section contract.** The builder calls `viewSection(context)` once and places what it returns at the Q1 slot; it never calls it for a delayed spawn. Section items are view-only: no catalog entry, no ID, never on a quick-command list (Q3). Their item builders move from `MenuCatalog` to `src/Yaat.Client.Core/ContextMenus/CanvasMenuItems.cs` and take the canvas state as arguments: `DataBlockForm(bool minified, Action toggle)`, `ResetDataBlockPosition(bool moved, Action reset)`, `NavRoute(bool shown, Action toggle)`, `Measure(MenuMeasureState state, string callsign, Action pick)`, `TaxiRoute(TaxiRouteDisplayMode mode, Action<TaxiRouteDisplayMode> set)`, `HideDataBlock(bool hidden, Action toggle)`, `DrawRoute(string label, Action enter)`, the sending `LeaderDirection`, `JRing`, `Cone`, `Blank`, `Unblank(MenuContext, IMenuHost)`, and `Display(IReadOnlyList<IReadOnlyList<MenuItem?>> blocks)`, so their labels stay headlessly testable.
  - Radar section (`RadarView.ContextMenus.cs`): Display ▸ (Mini or Full datablock, Reset datablock position, Show or Hide nav route, Measure from or to {cs}; Leader direction, J-ring, Cone; Blank, Unblank target), then Draw route.
  - Ground section (`GroundView.axaml.cs`): Display ▸ (Taxi route ▸, Hide datablock, Reset datablock position, Measure from or to {cs}), then Draw taxi route… (`CanDrawTaxiRoute`) and Push route… (`CanPushBack`).
  - List section: none (`_ => []`).
  - Leader direction, J-ring, cone and blank stay in the radar's section: the ground renderer draws none of them (no match under `src/Yaat.Client/Views/Ground/`).
- **Point clicks.** A right-click on empty map (radar) or on a taxi node or runway threshold (ground) with an aircraft selected goes through the same builder with `click.Point` set and `Callsign` the selected aircraft. The point items follow predicates, not the view: airborne, Fly heading {bearing to the point}, Direct to, Append direct to and Hold at {FRD} left and right; on the ground at a taxi node, Taxi here (`GetTaxiChoices`, with today's hover preview), Push to {stand or spot} (node Parking or Spot and `CanPushBack`), Custom taxi… (the input popup with an initial text and caret from today's `BuildCustomTaxiPrefill` rules); controllable, Warp here (`WARPG #node` at a node, else the warp popup seeded with the FRD). The view's point section follows: radar FRD row, Copy FRD, markers, Measure from or to here, measurement removal, MVA row; ground Measure from or to here, measurement removal, Draw taxi route… and Push route… from the node. With nothing selected only the point section shows, as today. Whether the point menu also carries the aircraft's full menu is Q2.
- **Delayed spawn and surface shadow** are branches of the one builder, read from `IMenuAircraft` (`IsDelayed`, `IsLiveTraffic` and `CanAssume`) on every view. Neither canvas draws a delayed aircraft (GroundCanvas.cs:1116), so in practice only the list opens its menu.
- **The list's previous selection** mirrors the canvases' rule (RadarView.ContextMenus.cs:71-80): the row selected at the right-click when it is not the right-clicked one. The grid stays single-select (`DataGridView.axaml`:31, user ruling), so `Selection` is the clicked row and the "two or more" paths (Assume selected live traffic (N), RPO items for several rows) are reachable only from tests. The list keeps its selection through the right-click and reads the clicked row from the event source (brief 3).
- **A view after the refactor** resolves the aircraft and the click, builds its section, calls `AircraftMenuBuilder.Build(ac, click, new ClientMenuHost(main, ac, anchor), section)` and shows the menu.
