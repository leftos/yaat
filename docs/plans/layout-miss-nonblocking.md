# Non-blocking runtime layout miss (YAAT-187)

Design input for the feature branch `feat/layout-miss-nonblocking`: the invariant pass (actors, invariants, every call site with its verdict, the interface and the recorded admission, the tests). Line numbers are against yaat d270517fe and yaat-server 17e8d13ec, so re-anchor before a brief. The owner rulings are in YAAT-187.

## Findings first
1. The engine reads the room pin (`PinnedAirportGroundData`, `ScenarioLifecycleService.cs:1220`→`:1270`), whose `Pin()` is `_layouts.GetOrAdd(faa, ReadLive)` (`RoomResourcePin.cs:176-177`) and never replaces an entry. A service returning null while loading would pin "no map" for the room, into checkpoints/exports as `MissingLayoutAirportIds` (`RoomResourcePin.cs:119-120`). The pin changes first.
2. Main risk is replay determinism: live sees "loading" for some ticks, a replay over a full pin sees the layout at once. Commands are recorded with their live verdict (`ActionRouter.cs:447-462`) and re-run; a TAXI refused live would be accepted on replay (`replay-fidelity` warning, `ActionRouter.cs:500-510`). Situation flags and arrival spacing are snapshotted (`SimulationEngine.Tick.cs:294-295, 317-326`). The tick oracle cannot see it (`docs/snapshots-and-replay.md:575`). So the second a layout becomes visible must be recorded.
3. "From the tick after it lands" fits `OpenSecond` (`SimulationEngine.Spine.cs:51-60`): admit landed layouts there and record each admission there.
4. Two more blocking paths: commands run under the room gate the tick loop waits on (`TrainingHub.cs:1138`, `RoomTickLoopService.cs:117`); `ExportRoomAsScenario` reads shadows' airports through the pin under the gate (`TrainingHub.cs:796/807`→`:831`→`ScenarioExporter.cs:638`).

## Invariants
- I1 nothing reachable from the tick thread or a gated command waits on a fetch; structural: the engine's interface has no blocking member (broken at `AirportGroundDataService.cs:166` via `:69/71/77`, `RoomResourcePin.cs:172/174/267/271`).
- I2 at most one fetch per airport (holds: re-check under lock `:184-188`); start fetches only via `GetOrStartFetch`; an `Unreachable` answer needs a retry interval (like `VideoMapRetry` `:45/374`) or polls refetch at tick rate.
- I3 "loading" is never stored where it outlives the load: not the pin, not the missing list, not `Ground.Layout`, not `PushPlanStore`, never a dropped block/preset; no partial pick (`ResolveGroundLayout` nearer-of-two `SimulationEngine.Scenario.cs:217-256`; `Commands.cs:510`, `ActionArms.cs:89`, `CommandDispatcher.cs:1107` cache via `Layout ?? Resolve…`).
- I4 a landed layout becomes visible once, atomically, per room, at `OpenSecond`; the pinned instance never changes after.
- I5 the visible second is recorded and replayed by every replay kind (rewind, seek, archive load, export reconstruction, checkpoint restore); a snapshot taken while loading restores as loading.
- I6 failures are not permanent at the service (today an `Unreachable` null is served 30 min and pinned for the room) — owner decision 1.
- I7 log per fetch, never per poll (polls happen per aircraft per sub-tick in `BuildPhaseContext`, `SimulationEngine.Tick.cs:1777/1793`).
- I8 the fire-and-forget fetch never faults unobserved (`:239-256`, `:307`).
- I9 replay never fetches or admits on its own; admission comes from the tape.
- I10 manifest airports are visible from load (prefetched and pinned before commit, `ScenarioLifecycleService.cs:242-243`; manifest `ScenarioResourceManifest.cs:115-169`).
- Replay misses today only on: a `SessionRecording` load (no bundled layouts), a room restored without a pin (`ReloadForRewind`→`PinLiveCaches`, `:1164, 1240-1247`), an archive whose layout format isn't read. After the change those defer and log a replay-fidelity line.

## Recommended interface
```csharp
public interface IAirportGroundData
{
    /// Never blocks. Loaded: the layout (null = no map) and its GeoJSON, from one cache entry.
    /// Loading: the fetch is running, started or joined by this call.
    GroundDataRead Read(string airportId);
}
public readonly record struct GroundDataRead(bool IsLoaded, AirportGroundLayout? Layout, string? SourceGeoJson);
```
Replaces `GetLayout`, `GetSourceGeoJson`, `GetLayoutAndSource` (`:77-81`); no blocking member, compiler-enforced I1. Service: cached → Loaded (+ stale refresh); else `_ = GetOrStartFetch(faa, null, Remembered)` → Loading. Pin: pinned → Loaded; else pass Loading through unpinned, `GetOrAdd` a Loaded. Off-tick waits stay on the concrete service (`PrefetchAsync` returns the shared task, `:150`, `:192`). The 11 test/tool implementations return Loaded; no default interface method.
Engine: snapshotted per-room deferred-airport set + per-aircraft pending-attach intents (new fields omitted when empty, so snapshot-0 hash is unchanged). Protocol: first read not ready (live) → add to deferred set, record `RecordedLayoutDeferred(t, faa)`, return Loading; `OpenSecond` (live) → in sorted order, each now-Loaded airport: remove, record `RecordedLayoutAdmitted(t, faa)`, complete pending attaches; replay: both are pre-tick actions (extend `IsPreTickAction`, `SimulationEngine.Recording.cs:42`), never polls; loaded on first read → admitted at once, nothing recorded. New `RunProfile` member (e.g. `AdmitsLayoutsFromSource => Kind != Replay`).
Main risk: not server-only; Yaat.Sim needs two recorded actions, a spine slot and two snapshot fields, or rewinds/exports/archive loads drift silently. Secondary: partial/null layout cached at the four PROCEED sites; `Unreachable` retried at tick rate; one-shots dropped while loading. Rejected: server-only with null (breaks I3, I5); blocking with timeout.
