# xunit.v3 -> TUnit migration

Companion to [test-suite-speed.md](test-suite-speed.md), which owns the history of why the suite is
as fast as it is. **The baseline below supersedes that file's 2026-08-26 numbers** — the Sim suite
is now 57.2s and 489s CPU, not 92s and 1,358s.

Why this is being attempted: the suite passed 10k tests and the iterative loop feels slow. TUnit
offers source-generated discovery and parallel-by-default execution on the same
Microsoft.Testing.Platform runner already in use. The migration is being run in a worktree to
produce authoritative numbers rather than because a win was expected.

Status: **Phase 0 complete, Phase 1 not started.** Nothing merged, no test file converted.
TUnit 1.65.68. See the Handoff section at the end for exact state and the recommended next step.

**Bottom line so far:** the measured scheduling prize is **0.0s** — xunit is already at ~89%
scheduling efficiency and both scheduling models hit the same theoretical bound, so TUnit's
headline advantage cannot apply to this suite. The only remaining question worth spending effort on
is whether source generation regresses incremental build time.

## Verified findings

Everything below was measured, not read from documentation. The probe project is a 10-test
TUnit-only project of known composition (kept out of the repo); the counts are what it actually
selected.

### 1. TUnit and xunit.v3 cannot coexist at runtime — the migration is big-bang per project

They build together fine (which is what lets the `TUXU0001` code fixer's analyzers load), but the
resulting executable throws before running a single test:

```
System.InvalidOperationException: The test framework adapter factory has already been registered
   at Xunit.MicrosoftTestingPlatform.TestPlatformTestFramework.RunAsync(...)
   at Yaat.Sim.Tests.AutoGenerated.XunitAutoGeneratedEntryPoint.Main(...)
```

Microsoft.Testing.Platform hosts exactly one test framework per process, and both packages
generate an entry point that registers one.

**Consequence for the plan:** a project cannot be converted incrementally. There is no state in
which some files are TUnit, some are xunit, and the suite runs. Between "start converting" and
"xunit package removed" the only available feedback is the compiler. Verify mechanisms in a
separate probe project first — the cost of discovering a bad assumption after converting 840 files
is the whole conversion.

### 2. `ITestOutputHelper` survives with zero per-file edits, via a global using alias

492 references across ~400 files, 335 of them primary-constructor declarations
(`class FooTests(ITestOutputHelper output)`). TUnit has no constructor injection of an output
helper, so the obvious reading is that every one of those declarations changes.

It does not. `[ClassDataSource<T>]` feeds a primary constructor, and a global using **alias**
makes the existing spelling bind to our own concrete type:

```csharp
// GlobalUsings.cs - one line
global using ITestOutputHelper = Yaat.Sim.Tests.Helpers.TestOutputHelper;
```

```csharp
public sealed class TestOutputHelper
{
    public void WriteLine(string message) => TestContext.Current?.OutputWriter.WriteLine(message);
    public void WriteLine(string format, params object[] args) => WriteLine(string.Format(format, args));
}

[ClassDataSource<TestOutputHelper>(Shared = SharedType.None)]   // <- the only line added per class
public sealed class FooTests(ITestOutputHelper output) { }      // <- unchanged
```

Verified working for both the primary-constructor form and the classic
`public FooTests(ITestOutputHelper output)` form with a constructor body.

**Ordering constraint:** the alias must NOT be added while xunit is still referenced. A using alias
outranks a type imported by `using Xunit;`, so introducing it early breaks every file that still
passes a real `Xunit.ITestOutputHelper` to `AddXUnit(...)`. Alias and xunit removal land together.

### 3. The constructor-pinning race protocol survives

`docs/test-harness.md` §"The static-singleton race protocol" depends on the test class constructor
running before each test body, so `TestVnasData.EnsureInitialized()` pins the process-global
singletons. TUnit constructs a **fresh instance per test** and runs the constructor before the
body — verified with a static counter asserting it had incremented more than once across two tests
in one class. The protocol ports unchanged.

Note this does not make the races go away: TUnit parallelises per test rather than per class, so
there are strictly more concurrent initializers than xunit produced. Watch for the documented
symptom (`Expected 98 / Actual 96.5` — a default-fallback read racing a mid-flight `Initialize`).

### 4. `[NotInParallel(key)]` genuinely serializes across classes

Verified with two classes sharing one key, each incrementing a shared counter and asserting it saw
no concurrency. This is the replacement for `[Collection("NavDbMutator")]` (97 classes) and
`[CollectionDefinition("Acceptance", DisableParallelization = true)]`.

### 5. Filter translation — verified against known cardinality, and one documented form is wrong

Exclusion semantics match xunit's: **untagged tests survive an exclusion filter**, which is what
`tools/test-all.ps1` and four CI workflows depend on.

Probe: 10 tests, 1 tagged `Category=Nightly`, 1 tagged `Category=PathfinderGrid`, 8 untagged.

| Intent | xunit.v3 (today) | TUnit `--treenode-filter` | Selected |
|---|---|---|---|
| everything | *(none)* | `/*/*/*/*` | 10 |
| exclude one category | `--filter-not-trait "Category=Nightly"` | `/*/*/*/*[Category!=Nightly]` | 9 |
| exclude two (the `test-all.ps1` default) | two `--filter-not-trait` flags | `/*/*/*/*[(Category!=Nightly)&(Category!=PathfinderGrid)]` | 8 |
| include one category | `--filter-trait "Category=Nightly"` | `/*/*/*/*[Category=Nightly]` | 1 |
| one class | `--filter-class "*.ClassicCtorTests"` | `/*/*/ClassicCtorTests/*` | 2 |
| class substring | — | `/*/*/*Serialized*/*` | 2 |
| method substring | `--filter-method "*Ctor_Runs*"` | `/*/*/*/*Ctor_Runs*` | 2 |
| **several method patterns** | `--filter-method "*A*" "*B*"` | `/*/*/*/(*A*\|*B*)` | 3 |

**Footgun — two wrong OR spellings, neither of which errors:**

| Spelling | Selected | Should be |
|---|---:|---:|
| `/*/*/*/*A*\|/*/*/*/*B*` | **10** (everything) | 3 |
| `/*/*/ClassA/*\|/*/*/ClassB/*` — *TUnit's own documented "Multiple filters (OR)" example* | **2** | 3 |
| `/*/*/*/(*A*\|*B*)` | 3 | 3 |

A top-level `|` between whole paths does not OR them; alternation only works **inside one path
segment**. TUnit's error text says so when it rejects a parenthesised variant ("To combine
alternatives for one path segment, use syntax like `/A/B/C/(X|Y)`") — but the two forms above are
accepted silently and select the wrong set.

Both failure directions read as green downstream. Every translated filter must therefore be checked
by **count** against the xunit form, not by inspection — which is why the verification section
below compares `--list-tests` output between branches rather than eyeballing summaries.

## Measurement harness

TUnit from the csproj and picks the filter syntax), so the migration branch can be diffed against
`main`. Metrics: `discovery`, `one-class`, `sim-run` (wall + process CPU + CPU/wall ratio),
`incr-build-test`, `incr-build-sim`, `cold-build`, `full-gate`.

## Baseline — xunit.v3 at `origin/main`, 2026-09-03

Release, 16 logical processors, quiet machine, median of 3 runs. Worktree was rebased onto
`origin/main` first, so this is the branch the migration will be diffed against.
Reproduce with `pwsh tools/measure-test-loop.ps1 -Label <name> -Runs 3`.

| `sim-run` (unfiltered, 10,586 tests) | 71.9s | 584.9s | 72.2 / 69.6 / 71.9 | CPU/wall 8.1x |

`sim-run-dev` — Nightly and PathfinderGrid excluded — is the number to compare against, because it
is what developers and per-PR CI actually run. Read `sim-run` only as a curiosity: those two
categories are just 4 test methods, but each drives a large internal sweep.

The iterative fixed floor is **~2.3s** (process start + `ModuleInit`'s CIFP/NavData warm +
reflection discovery). Enumerating all 9,157 tests adds only ~1.1s on top. That ~2.3s is the whole
budget TUnit's source-generated discovery competes for, and it can only address the discovery
slice — not the navdata warm, and not the build.

Note these numbers supersede the 2026-08-26 figures in `test-suite-speed.md`: the Sim suite is now
57.2s (was 92s, then 80s after Server GC) and its CPU is 489s (was 1,358s). The optimisations
listed there worked.

### The scheduling prize is zero — measured, not assumed

CPU/wall fell from 14.8x to 8.6x between August and now, which looks like 46% of the cores going
idle and therefore like headroom a per-test scheduler could reclaim. **That reading is wrong**, and
it is worth writing down because it is the natural one: CPU/wall measures how CPU-bound the tests
are, not how well the scheduler packs them. The optimisations removed CPU work (−64%) faster than
they removed wall time (−38%), so the ratio fell while the schedule stayed just as full.

`tools/analyze-test-schedule.py` settles it from a TRX of per-test durations. It simulates LPT
packing onto 16 workers under both models — xunit's (a class is a collection; its tests run
sequentially) and TUnit's (per test):

```
tests 9363 · classes 846 · total test-work 811.0s · workers 16

perfect divisibility     50.7s   (811 / 16 - unreachable lower bound)
longest single test      21.1s   (hard floor for ANY scheduler)
longest single class     36.3s   (hard floor for a per-CLASS scheduler)

LPT per-class  (xunit model)     50.7s
LPT per-test   (TUnit model)     50.7s
scheduling prize                  0.0s  (0.0%)
```

Both models land on the divisibility bound. The heaviest class (`GroundBrainE2ETests`, 36.3s over
4 tests) is still *below* 50.7s, so per-class grouping never becomes the binding constraint —
there is always enough independent work to fill all 16 workers either way.

Actual 57.2s against a 50.7s optimum is **~89% scheduling efficiency** (811 / 57.2 = 14.2 of 16
workers busy). So xunit's scheduler is already near-optimal here, and **TUnit's parallel-by-default
model has no room to win on this suite.** Any gain must come from the ~2.3s fixed floor or from
build time — and the build is where source generation adds cost rather than removing it.

Re-run this analysis against the TUnit branch before Phase 2's gate: if the measured TUnit wall
time beats 50.7s, the model is wrong and should be re-examined rather than believed.

### The build-cost gate — FAILED, measured

The remaining question was whether source generation regresses incremental build at this scale.
It does, by a lot, and the penalty grows with test count.

Method: `<scratchpad>/gen_suite.py` emits a synthetic project matching the real suite's *shape*
(846 classes, ~11 cases each, 47% taking an output helper via `[ClassDataSource]`) in either
framework, with trivial test bodies — generator work scales with test/class count, not with what
tests do, so this measures compile cost without converting 840 real files first. Median of 3
(2 for the sweep), Release.

| Classes | Cases | xunit cold | TUnit cold | xunit **incr** | TUnit **incr** | Delta |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 1,100 | 1.5s | 2.4s | 1.3s | 2.3s | +1.0s |
| 400 | 4,400 | 2.1s | 4.7s | 2.1s | 4.2s | +2.1s |
| **846** | **9,306** | 2.3s | 7.8s | **2.1s** | **7.2s** | **+5.1s** |

"incr" = touch one test file, rebuild the project. A no-op rebuild is ~1.0-1.3s for both, so this
is real generator work, not MSBuild overhead.

xunit's incremental cost is flat in test count; TUnit's grows roughly linearly. At the current
9,363 tests the penalty is **~+5s on every edit**, and it scales with exactly the thing that
prompted this evaluation — the suite growing (8,686 -> 9,363 in about a week).

### Verdict

Against the plan's four success criteria:

1. *Sim run time drops* — cannot: the scheduling prize is 0.0s and the fixed floor is ~2.3s, of
   which only the discovery slice is addressable.
2. *Incremental build does not regress materially* — **fails**, +5.1s per edit and growing.
3. *Full gate does not regress* — would inherit the build regression.
4. *No test-count drift or new flakes* — untested; moot.

Net effect on the loop this work set out to speed up: today an edit plus a filtered class run is
~3.3s build + 2.3s run ≈ **5.6s**. Under TUnit it becomes roughly 8.4s build + ~2s run ≈
**10.4s** — close to 2x slower per iteration.

**Recommendation: do not migrate.** The gate in the plan says stopping here is a successful
outcome, and it is: the question is answered with numbers rather than intuition, and the two tools
that answered it are reusable for the next such question.

What actually would speed up the loop, in order of expected value, all framework-independent:

- The ~2.3s fixed floor per filtered run is mostly process start + `ModuleInit`'s CIFP/NavData
  warm. That is ours to optimise and is paid on every single iteration.
- The 305 tests >1s (89% of CPU) are `Replay(recording, N)` seeks from t=0; converting suitable
  ones to hybrid replay is the open follow-up already listed in `test-suite-speed.md`.
- `SegmentExpander.RunBoundedDetour` (>1s for one TAXI resolution), also already listed there.

### The decision this is now sitting on

The evidence has moved **against** the migration since the plan was approved, and it moved for a
reason that did not exist when the plan was written:

- The scheduling prize is **measured at 0.0s**. xunit is at ~89% scheduling efficiency and both
  scheduling models hit the same 50.7s bound. TUnit's headline advantage cannot apply here.
- The remaining addressable budget is the ~2.3s fixed floor per filtered run, of which only the
  discovery slice is TUnit's to win.
- Against that, `incr-build-test` is 3.3s today and source generation adds work to exactly that
  metric — with a documented `Collect()` fan-in that regenerates ~1,000 helper files per edit at
  10k tests.
- The conversion is big-bang per project (xunit and TUnit cannot both run), so there is no partial
  landing and no incremental verification.

That is not a reason to stop unilaterally — the migration was chosen deliberately, in a worktree,
to produce authoritative numbers, and it would still produce them. But the cheapest remaining way
to answer the one open question is no longer the full conversion:

**Recommended next step: measure `incr-build-test` for a source-generated 8,686-test project
before converting anything.** Generate a synthetic TUnit project of that size, touch one file,
rebuild, and compare against the 3.3s baseline. That answers the decision gate in maybe an hour
instead of a full conversion, and if it regresses badly the conversion is moot.

If the answer is "no regression", then proceed with Phase 1 exactly as written below.
