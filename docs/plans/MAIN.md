## Bug reports and feature requests

- [ ] **SFO LC VFR transitions orbit at the Class B border** (Discord, Michael B, 2026-09-25): VFR transition aircraft did 360s at the boundary, and a fly-heading made them turn back just as fast, until the controller used the cleared-into-Class-B command. Explored 2026-09-25: this cannot happen in RPO mode, because `PilotProactive.TickAirspaceBoundaryRespect` returns early unless `SoloTrainingMode` is on, and RPO is `!SoloTrainingMode`. The bug is solo-only. `AirspaceBoundaryHoldPhase.OnTick` ends the orbit on any `FH` and `OnEnd` keeps the heading, but on the next `TickPilotProactive` second the same function sees the gate still unsatisfied and installs a fresh hold, which turns away from the boundary without saying anything. 7110.65 §7-9-2 Note 1: a heading is not a Class B clearance, so refusing to enter is right. The gap is the silent re-arm: there is no "unable" transmission like `AnnounceUnableAssignedAltitude`. How the pilot should answer a vector into Class B without a clearance (announce "unable", then hold, or fly the heading to the boundary first) is owed an `aviation-sim-expert` ruling. The red test goes in `Issue308AirspaceLevelOffTests`, next to `Orbit_EndsWhenTheControllerVectors`: install the hold, give an `FH` toward the boundary, run the hold to completion, tick again, and assert that no new hold reverses the heading. Follow-up from the reporter: they were probably in solo mode, and no pilot request showed up as a radio bubble. In solo mode a pilot needing a Class B clearance should call up to request it (heard by TTS and shown as a bubble). Check that the hold's request transmission is queued and reaches the client's bubble. No bundle; the reporter will save one next time.
