# Client driver MCP server

`tools/Yaat.ClientDriver.Mcp/` is an MCP stdio server that lets an agent drive the **real** YAAT desktop client, and a running CRC: enumerate windows and controls, click, type, take a screenshot of a window, read the client log. A YAAT client it launches is driven over the client's own automation pipe, without ever taking the foreground (**Background driving** below); CRC, and a YAAT client started without automation mode, are driven through Windows UI Automation. It exists for UI-path bugs that a view-model test cannot reproduce (a menu item that does nothing, a dialog that never opens) and for comparing what CRC draws against what YAAT shows for the same aircraft.

Windows only (`net10.0-windows`, `System.Windows.Automation`); `EnableWindowsTargeting` keeps it building in the Linux CI solution build.

## Running it

`.mcp.json` at the repo root registers it for Claude Code as `yaat-client-driver`:

```json
{ "type": "stdio", "command": "pwsh", "args": ["-NoProfile", "-File", "tools/Yaat.ClientDriver.Mcp/launch.ps1"] }
```

- **Build it once per clone, and after changing it:** `dotnet build tools/Yaat.ClientDriver.Mcp`. The launcher never builds: stdout is the protocol channel, and MSBuild output would corrupt it. Nothing reaches stdout before the first JSON-RPC frame; all logging goes to stderr.
- **It runs from a copy, not from `bin/`.** `launch.ps1` copies the build output to `%LOCALAPPDATA%/yaat/client-driver-mcp/run-<launcher pid>/` and starts `dotnet <copy>/Yaat.ClientDriver.Mcp.dll`. A server running out of `bin/` locks its own exe and dlls, and the solution build — which prek runs on every commit — then fails with `MSB3027`. Copies whose launcher has exited are pruned at the next launch. A running session keeps the build it started with; reconnect the server (`/mcp`) to pick up a rebuild.
- Claude Code reads `.mcp.json` at session start and asks once to approve a project server.
- The server's working directory is the repo root, so the relative defaults below resolve there.
- `launch_yaat` needs a built client: `dotnet build src/Yaat.Client`.
- A client started by hand with `YAAT_AUTOMATION=1` and `--autoconnect http://localhost:5130 --scenario <vNAS scenario id>` comes up never-activated, connected, in a room and with the scenario loaded, with no input. The scenario starts paused: send `UNPAUSE` or `SIMRATE n` over the pipe.

## Rules for a driving session

- **One driver per application.** YAAT.Client and CRC are single-instance applications, so no two agents drive the same one at the same time. One agent may drive YAAT and CRC together. An orchestrator never dispatches a second agent that would drive an application another running agent is driving; nothing in the server enforces this yet (the plan tracks a lock).
- **Close what you opened.** A CRC or YAAT client an agent started for a session (through `launch_yaat`, `Start-Process`, or anything else) is stopped by that agent when the session ends, along with any yaat-server it started. A CRC the user already had running is left alone.

## Tools

| Tool | What it does |
|---|---|
| `launch_yaat(appDataDir, exePath, waitSeconds, env)` | Starts `Yaat.Client.exe` (only that file name) in automation mode (`YAAT_AUTOMATION=1`) with `YAAT_APPDATA_DIR` pointed at a scratch directory (default `.tmp/client-driver/appdata`), so the developer's preferences and favorites stay untouched. `env` adds environment variables to the client, each `KEY=VALUE` (e.g. `YAAT_DEV_SOLO_SPEECH_BUBBLES=1`); an entry with no `=`, an empty key, a null, a key given twice, or `YAAT_APPDATA_DIR` / `YAAT_AUTOMATION` in any case is refused with `INVALID_PARAM`. Waits for the automation pipe to answer with a window list, and returns the pid, that window list and the log path. |
| `list_processes(nameContains)` | Finds processes to attach to — `Yaat.Client`, `CRC`. |
| `list_windows(pid)` | Every top-level UIA window of a process, with an element id each. Each row ends `| hwnd=0x<HEX>`, the window's native handle (a recorder captures by it; `0x0` when the platform gives none, always for a YAAT overlay popup). |
| `dump_tree(elementId, maxDepth)` | Control-view tree under an element, one line per node (capped at 400 lines). |
| `find_elements(rootElementId, name, automationId, controlType)` | Descendants matching every criterion given (at least one is required), at most 50. |
| `get_value(elementId)` | `ValuePattern` value of a text box. |
| `screenshot(windowElementId, maxWidth)` | Captures the element's rectangle, returns the PNG inline and saves it under `.tmp/client-driver/shots/`. A pipe id is rendered by the client itself at its render scale, whatever covers it; through UI Automation, virtual mode renders the window into the image (`PrintWindow`) and real mode brings it to the foreground and copies the screen. |
| `wait_for(selector, condition, pid, text, count, timeoutMs)` | Pipe only. Polls inside the client every 100 ms until `exists`, `not_exists`, `visible`, `enabled`, `text_equals`, `text_contains` or `count_equals` holds on the selector's matches; `timeoutMs` is clamped to 100–30000, and a miss fails with `TIMEOUT` and the last match count. |
| `batch_drive(steps, pid)` | Pipe only. Runs 1–100 steps in order against one client, one pipe call each, and stops at the first failure; the whole batch is cut after 300 s. A step is `{"method": "<any pipe method>", "params": {…}}` (params forwarded as-is, a numeric `params.timeoutMs` sets how long its answer may take, plus 5 s), `{"assert": "wait", "selector", "condition", "text"?, "count"?, "timeoutMs"?}` (the pipe's `wait_for`, default 1000 ms, clamped 100–30000) or `{"assert": "no_errors"}` (fails on client errors logged since the batch began or the previous `no_errors`). Steps address elements by selector: a `nodeId` or `windowNodeId` is refused, since ids go stale between steps. A `screenshot` step saves the PNG under `.tmp/client-driver/shots/` and returns its path. The result is JSON, never a tool error: `{passed, steps: [{index, method or assert, ok, elapsedMs, result or error}], failedAt}` (`failedAt` only on a failure; later steps are not listed); read `passed`, not the result's error flag. |
| `wait_until(conditions, pid, mode, timeoutMs, screenshot, then)` | Pipe only. Polls the client's own simulation state every 100 ms until a condition list holds: `on_ground`, `landed` (seen airborne, then on the ground), `phase_is` / `phase_is_not` (each with `callsign`, plus `phase`), `queue_empty` (`callsign`), `log_matches` (`pattern`, a .NET regex matched case-insensitively with the non-backtracking engine, optional `callsign`; it skips terminal lines replayed from a loaded recording's history) and `sim_seconds` (`atLeast`). `mode` is `any` (default) or `all`; `timeoutMs` is clamped to 100–600000 (default 30000). When met, the client takes the optional capture first (`{"windowSelector": …}` or `{"selector": …}`), then runs the `then` actions in order (`{"action": "pause"}`, `{"action": "set_rate", "rate": n}`); `{"action": "stop_recording"}` is run by this server after the client answers, only when met, and stops the running recording after a final `wait_until met` mark at the match's sim time. A timeout is a result, not an error: the text says `met after <N> ms at sim <S> s: held <kinds>` or `not met in <N> ms at sim <S> s`, one `- [<index>] <kind>: <last value>` line per condition, a `then <action>: ok` / `failed — <error>` line per action, and `screenshot: <path> (<W>x<H>)` (saved under `.tmp/client-driver/shots/`) or `screenshot failed: <error>`. |
| `list_app_tools(pid)` | Pipe only. Lists the client's app tools: its own setup actions, marked `[AutomationTool]` in `src/Yaat.Client/Automation/Tools/`. The first line is `N app tools (pipe)`, then one line per tool: `- name(param: type — description; …): description [available]` or `[unavailable: <reason>]`. While the main window is not up, every tool reads unavailable. |
| `call_app_tool(tool, arguments, pid)` | Pipe only. Calls one app tool by name with `arguments`, a JSON object keyed by parameter name (types `string`, `int`, `double`, `bool`; every parameter required). An unknown tool, a missing or unknown argument, or a value of the wrong JSON kind is an `INVALID_PARAM` error naming it; a tool that cannot run now prints `<tool> unavailable: <reason> (pipe)`, otherwise `<tool>: <message> (pipe)`. Waits up to 120 s, since `load_recording` answers once the room has loaded. The tools: `set_sim_rate(rate)`; `center_radar(callsign, rangeNm)` (the primary radar, range 1–256 NM, not saved to the scenario's settings); `set_video_map(starsId, enabled)` (sets the map to that state; unavailable until the maps load, and `center_radar` until the radar has restored its settings); `set_solo(enabled)` (the toggle's own path; the message says the change is requested; the room's settings broadcast confirms it); `load_recording(path)` (the Load Recording command without its file dialog); `place_rbl(from, to)` (a range-bearing line on the primary radar between two endpoints, each a callsign, fix or FRD; the `.rbl A B` command's own path, so an unresolvable endpoint or a full 15-slot store answers unavailable with the command's error; returns the slot), `remove_rbl(slot)`, `clear_rbls()` (the `.norbl` path, so ground-view lines go too); `set_leader_direction(callsign, direction)` (sends `LDR 1-9`; the message says when the student leader direction sync preference is off, since the radar then does not show it); `set_datablock_offset(callsign, dxPx, dyPx)` and `reset_datablock_offset(callsign)` (the client-local drag offset on the primary radar, through the same `DataBlockViewState` methods the drag uses). An unknown callsign answers unavailable. |
| `record_start(pid, windowElementId, out, fps, audio)` | Records one window to an MP4: one ffmpeg reads `tools/Yaat.WindowRecorder`'s video pipe (Windows.Graphics.Capture by window handle) and, when `audio` is on, the process's own audio, and crops each frame to the client area (the title bar and borders measured from the window, no crop to type). Exactly one of `pid` (its main window: the first top-level window with a native handle, preferring a title starting YAAT or CRC) or `windowElementId` (from `list_windows`). `out` defaults to `.tmp/client-driver/recordings/<pid>-<yyyyMMdd-HHmmss>.mp4`, must end in `.mp4`, and is never overwritten; `fps` 1–60 (default 30); `audio` defaults to on for a YAAT client with an automation pipe and off otherwise (CRC). Encodes with `h264_nvenc` when a probe frame succeeds, else `libx264`. Refuses a minimized window, a second recording, and a missing ffmpeg, and fails when the pipeline dies within 300 ms. One recording per server; it ends at `record_stop`, at `wait_until`'s `stop_recording`, after one hour (or when the window closes or resizes; the next start or stop notes it), or when the server shuts down, which waits for the MP4 as a stop does. Paths reach the `cmd` pipeline through `YAAT_REC_*` environment variables, so a `%` in a path is never expanded. `<clip>-recorder.log` and `<clip>-ffmpeg.log` sit beside the MP4. |
| `record_mark(label)` | Marks the current moment of the running recording and rewrites `<clip>-marks.json` (`{pid, hwnd, fps, startedUtc, marks: [{label, wallUtc, clipSeconds, simSeconds}]}`): `clipSeconds` is null before the first frame, `simSeconds` is the YAAT client's scenario clock from `get_sim_time` (null for CRC or after 2 s without an answer). A pipeline that died is reported with its exit code and the recorder's last log lines, and the recording ends. |
| `record_stop()` | Stops the recording: waits up to 15 s for the recorder (past that it alone is killed, so the clip runs up to 15 s past the stop), then up to 120 s for ffmpeg to finish the MP4 (past that the pipeline is killed and the MP4 may be unplayable); a cancelled stop still lets the encode finish. Returns the MP4's path, its length, the frames written, the frames dropped (fps × length − written) and the marks file. |
| `queue_file_pick(path, cancel, pid)` | Pipe only. Queues one answer (a path, or a cancel) for the next file dialog the client opens; each dialog takes the oldest answer, and one opened on an empty queue fails at once. |
| `set_input_mode(mode)` | `virtual` (the default) or `real`, for the whole server; see **Input modes** below. |
| `invoke(elementId)` | `InvokePattern` — buttons. |
| `click(elementId, button, doubleClick, modifiers)` / `click_point(x, y, …, windowElementId)` | A mouse click at the element's centre; `click_point` clicks a point, for surfaces UIA cannot see into (the radar and ground views, CRC's scopes). Over the pipe the click runs the control's own action first (command, toggle, menu item) and holds any of `ctrl`, `shift`, `alt`, `meta`; `click_point` with a pipe window id takes DIPs from that window's client area. Through UI Automation `click_point` takes screen pixels and `modifiers` (`shift`, `ctrl`, `shift+ctrl`) works in real mode only. |
| `set_text(elementId, text)` / `send_keys(keys, focusElementId)` / `focus(elementId)` | Text entry. `send_keys` takes SendKeys syntax (`{ENTER}`, `^a`, `%{F4}`); virtual mode accepts only plain characters, braced literals such as `{+}`, and `{ENTER}` `{ESC}` `{TAB}` `{BACKSPACE}`/`{BS}` `{DEL}` `{HOME}` `{END}` the arrows and `{F1}`–`{F12}`. |
| `tail_yaat_log(appDataDir, lines)` | Tail of `<appDataDir>/yaat-client.log`. |
| `stop_process(pid)` | Closes, then kills, a client this server launched (matched by pid **and** start time) or any process named `Yaat.Client`. It never stops anything else — CRC included. |

### Input modes

- **`virtual` (default).** Clicks and keys are posted as window messages (`WM_MOUSEMOVE`, `WM_LBUTTONDOWN`…, `WM_KEYDOWN`/`WM_KEYUP`, `WM_CHAR`) straight to the YAAT window. The real mouse pointer never moves and the foreground window never changes, so the developer can keep working while an agent drives the client. It also works when an elevated window holds the foreground, which makes Windows refuse `SetCursorPos`/`SendInput`. Screenshots use `PrintWindow`, so a covered window captures correctly. It reaches YAAT windows only; CRC needs `real`. Avalonia reads Shift/Ctrl from the keyboard state rather than from the message, so a modified click or a `^`/`%`/`+` key is refused, not sent unmodified. `set_text` focuses with a posted click, then types (End, one Backspace per character, the text). A posted click never uses UIA `SetFocus` or `ValuePattern`, since both can take the foreground.
- **`real`.** `SendInput` / SendKeys, as a user would: the cursor moves and the window is brought to the front, so a video shows the pointer. Typing refuses, rather than sending keys to whatever else is in front, when the target did not take the foreground.
- Every input tool's result ends with `(virtual)` or `(real)`, or `(pipe)` for a client driven over its automation pipe. The client drops input while navigation data loads, for ~10 s after launch in both modes; wait for the status bar's "Navigation data loaded".

Element ids (`e1`, `e2`, …) come from `list_windows` / `find_elements` / `dump_tree` and live as long as the server process. A described element reads `e2 | ControlType.Edit |  | id=CommandInput | enabled=True | rect=(2008,984 996x25)`.

## What the YAAT client exposes

- The main window's title is `YAAT`. Avalonia maps `x:Name` to the UIA AutomationId: `CommandInput` (the command box), `ConnectMenuItem`, `DisconnectMenuItem`. Menu items without an `x:Name` are found by Name (the header without its `_` accelerator).
- **Menus need clicks.** `ExpandCollapsePattern` is unsupported on Avalonia menus, and a menu's items do not exist until it is open: `click` the menu, then `find_elements` under the **main** window, where UI Automation files the popup and its items; `list_windows` never lists the popup. At the Win32 level the popup is its own owned `WS_EX_TOOLWINDOW` window, and in virtual mode a click on one of its items is posted to that window.
- **File dialogs.** A client in automation mode opens no dialog: `queue_file_pick` the path before the action that opens it. A client driven through UI Automation shows the native picker, which runs in `PickerHost.exe`, outside the client's windows, and cannot be filled by the driver's keystrokes (friction #21 in [`plans/client-driver-mcp-friction.md`](plans/client-driver-mcp-friction.md)); launch through `launch_yaat` instead.
- A button that "does nothing" usually logged `Unhandled UI-thread exception (recovered)`. Over the pipe it comes back with the call (**Client errors on every result** below); through UI Automation, `tail_yaat_log` first.

## Before launching: the scratch preferences

A room's ARTCC picks its scenario catalog. Room > Create Room uses the ARTCC picker in the lobby overlay (Training Rooms, beside its Create Room button) and falls back to the `artccId` preference, which a dev sign-in sets to `ZAB`; so the menu item creates ZAB rooms (ABQ scenarios only). Create the room from the lobby instead: `find_elements` the overlay's ComboBox, `send_keys` the ARTCC id (`ZOA` for OAK/SFO) with the ComboBox as `focusElementId` (its dropdown opens off the window's bottom edge, where a click on an item fails), then `invoke` the overlay's Create Room button (a posted click on it did nothing). The Load Scenario window's Local Files folder box is read-only and filled only by Browse (a native dialog, real input); set `lastScenarioFolder` in the same file to the folder holding the scenario instead. The client reads the file at startup, so edit it before launching, or stop the client, edit, and relaunch.

## Recording a demo

Used for the #462 push demo. Run yaat-server from source on `:5130`, `launch_yaat`, then File > Connect > "Local", Room > Create Room, and Scenario > Load Scenario > Local Files with an empty scenario for the airport. Spawn with the carrier named so the type and airline match (`ADD I L J @F8 CRJ7 *SKW`), and name the aircraft in every command (`SKW735 PUSH $7A`); a bare command goes nowhere without a selection. `set_text` on `CommandInput`, then a separate `send_keys {ENTER}`.

- **Window and view.** Resize the main window without activating it (`SetWindowPos` with `SWP_NOZORDER | SWP_NOACTIVATE`) to a 1920×1080 client area. Zoom by posting `WM_MOUSEWHEEL` to the main window at a screen point, one message per notch; there is no pan tool, so pan by zooming out at one point and back in at another (out at the top and in at the bottom moves the content up). Keep one zoom for takes that will be composited.
- **Capture.** `record_start` with the client's pid, `record_mark` at each moment worth finding again (the command, the readback), and `record_stop`, or a `wait_until` whose `then` ends with `stop_recording` so the clip ends at the condition rather than at a guessed duration. It runs `tools/Yaat.WindowRecorder` (a port of the `video-capture` skill's `WgcCapture`, same flags plus `--help`; the MCP's build copies it under `recorder/` in its output, found by `Recording/RecorderLocator.cs`) into one ffmpeg that reads the window's video and the client process's own audio, which carries the solo pilot's TTS, and crops to the client area itself. WGC delivers a frame only when the window redraws (one in 20 s on a static tab); the recorder's timer still writes a steady frame rate, and ffmpeg stamps each frame with its arrival time (`-fps_mode vfr`), so a clip whose recorder fell behind still plays in real time (`record_stop` reports the frames dropped). The marks file's `clipSeconds` lines each mark up with the clip for editing.
- **Edit.** Crop the ground view to 16:9, keep the command and readback at 1×, speed up the tow, caption the command with `drawtext`, and raise the voice (it records around −48 dB RMS). Several runs from the same start pose overlay cleanly with `blend=all_mode=lighten` on the dark ground view, each delayed a few seconds so the readbacks do not overlap.

## Background driving: the automation pipe

Driving YAAT never steals focus or jumps to the foreground while the user works:

- **An automation endpoint inside the client, local only.** With `YAAT_AUTOMATION=1` (one switch; `launch_yaat` always sets it) the client (`src/Yaat.Client/Automation/`) hosts the named pipe `yaat-automation-<pid>`, restricted to the current user, with a discovery file per PID (`%TEMP%/yaat-automation/<pid>.json`), on Zafiro.Avalonia.Mcp's line-delimited `{id, method, params}` protocol with coded errors and recovery hints. Its methods: `ping`, `list_windows`, `get_tree`, `click`, `click_point`, `send_keys`, `set_text`, `focus`, `screenshot` (`RenderTargetBitmap`), `wait_for`, `wait_until`, `queue_file_pick`, `list_app_tools`, `call_app_tool` and `get_sim_time` (`{simSeconds, isPaused, simRate}` from `IAutomationState`; `UNSUPPORTED_OPERATION` until the main window is up), all raised on the UI thread (`wait_until` reads the simulation through `IAutomationState`, `MainViewModelAutomationState` over the main view model, and runs its `then` actions off the UI thread). Selectors are Zafiro's CSS-like ones (`#Name`, a type name, `StackPanel > TextBox`), without its Roslyn `dc:` predicates (no Roslyn in the client).
- **Client errors on every result.** Since protocol 1.3.0 (`Protocol/ProtocolVersion.cs`; 1.4.0 adds `get_sim_time` and the windows' `hwnd`). The client keeps its last 200 Error and Critical log entries in a ring with sequence numbers (`Yaat.Client.Core/Logging/RecentErrorLog.cs`, registered by `AppLog`). Each response carries in `clientErrors` the entries logged from the call's start until its answer was ready, oldest first and at most 20, a handler failure's own entry included; the field is absent when there are none. `clientErrorsOmitted` counts the call's entries left out, by the cap or because the ring overflowed during a long call (absent when 0). Warnings are not attached. The capture is by time window, so an error another thread logs during the call comes back with it too, and a cancelled call carries nothing. In the MCP, `Pipe/PipeCallErrors.cs` is a call-tool filter, registered by `WithPipeCallErrors()`: every tool result that made pipe calls gets one more text block, `Client logged N error(s) during this call:` (with ` (M not shown)` before the colon when entries were omitted; N counts them too) and one `- [Level] Category: message (exception)` line each, on a success and an error result alike. A tool that throws a non-MCP exception after its pipe calls answers with the SDK's `An error occurred invoking '<tool>'.` plus the block, so a protocol-skew failure still shows the client's errors.
- **A never-activated window.** In automation mode windows show with `ShowActivated = false`, dialogs included, `OverlayPopups` is on, the client's own `Activate()`/`Topmost` calls are suppressed, and dialogs show non-modal (`DialogPresenter`) so Avalonia never activates an owner. Every such window, dialogs included, also carries `WS_EX_NOACTIVATE` (`AutomationGate.ApplyShowActivated`, through Avalonia's Win32 window-styles callback): `ShowActivated = false` shows a window with `SW_SHOWNOACTIVATE`, which leaves it activatable, and when the window in front of it is minimized Windows hands the foreground to the next top-level window in Z-order, which can be the client (a window that closes instead hands it back to the previous foreground, never to the client). Only `WS_EX_NOACTIVATE` stops that hand-off. A real click does not activate an automation-mode client either, so a person cannot type into it; a driver's `SetForegroundWindow` still works, and the style never applies outside automation mode. Windows stay Normal, since any visible `WindowState` change activates on Win32. The global key hook and Discord Rich Presence are off.
- **An injected file picker.** The client's storage-provider calls go to a pipe-answered picker; the agent queues paths with `queue_file_pick`, and a picker call on an empty queue fails at once.
- **Routing in the MCP.** A YAAT pid with a live pipe routes to it; everything else, CRC included, keeps the UI Automation driver unchanged, and `set_input_mode` does not affect pipe-routed calls. Out of reach in-app and left to the outside driver: push-to-talk through the SharpHook hook, drags, hover.
- **Montage video** is Windows Graphics Capture of a never-activated window kept behind the others, with the client's audio by per-process loopback.

## What CRC exposes

CRC is a WPF app (`CRC.exe`); its display windows are titled `CRC : <n>` or `CRC : <n> : <header>`. Its scopes (STARS, Tower Cab, ASDE-X, SAID, ERAM) are one OpenGL surface inside the window: UIA reaches CRC's windows, menus and dialogs but **not** tracks or datablocks. Read a scope with `screenshot`, act on it with `click_point`. An elevated CRC blocks injected input; the input tools then fail with an explicit "SendInput was blocked" error rather than reporting a click that never happened. CRC needs `set_input_mode real`, which shares the keyboard and mouse with whoever is at the desk. The first live session (profile setup, connect, a flight plan amendment) is written up in [`crc-first-session.md`](crc-first-session.md); the frictions it found are in [`plans/client-driver-mcp-friction.md`](plans/client-driver-mcp-friction.md).

## Scripts

- `pwsh tools/Yaat.ClientDriver.Mcp/smoke.ps1` — protocol only: starts the server, checks every stdout line is JSON and every tool is listed. Opens no window.
- `pwsh tools/Yaat.ClientDriver.Mcp/live-check.ps1` — launches a real client through `launch_yaat` (automation mode, every call over the pipe), asserts the launch left the foreground unchanged and the main window reads `active=False`, and sends no input. `-Background` also drives it over the pipe (opens and closes two menus, types into the command box, a `set_text` round trip, a click behind a modal refused with `ELEMENT_DISABLED`) and asserts the foreground window and the cursor never change. It then checks the `WS_EX_NOACTIVATE` hand-off: every client window carries the style (`<step>: N client windows carry WS_EX_NOACTIVATE`), and a console it starts in front of the client (`conhost.exe`, its own pid only) is minimized, asserted iconic, and the foreground sampled for a second must never be the client (`foreground hand-off after minimizing the window in front: … (client never took it)`); when the foreground then differs from the run's starting window it only warns. It needs a client window directly behind the console; if that precondition fails, run it again. The check takes the foreground for about 5 s, so ask before running it on someone's desktop. `-WithInput` starts the client itself without `YAAT_AUTOMATION` and runs the same steps over UI Automation with real input, so it takes the foreground and moves the cursor. If CRC is running it lists and captures its first display window.
- `McpStdio.ps1` — the dot-sourced JSON-RPC-over-stdio plumbing both scripts share.
