# Airspace Database & Boundary-Crossing Detection

> Read this before touching anything under `src/Yaat.Sim/Data/Airspace/`, `AirspaceBoundaryHoldPhase`,
> `PilotProactive.TickAirspaceBoundaryRespect`, `PilotProactive.TickBravoCap` (`Pilot/BravoCap*.cs`), `Pilot/BravoPathPredictor.cs`, or the Class B/C separation-minima path in
> `SoloTrainingEvaluator`. This is the point-in-polygon containment engine plus its two consumers.
> The proactive ticks run in the shared post-physics step, which both repos drive.

## What it is (and is not)

`AirspaceDatabase` is a lateral point-in-ring + vertical altitude-band containment engine over a fixed set
of FAA Class B and Class C airspace volumes, loaded from a checked-in GeoJSON fixture. It answers three
questions for solo-training pilot AI and scoring:

1. *Is this aircraft currently inside a Class B/C volume?* — `FindContaining(position, altitudeFtMsl)`.
2. *Will this aircraft's projected track cross into a Class B/C volume within N seconds?* — `FindFirstProjectedEntry(...)`.
3. *Which separation minima apply to this pair right now?* — used indirectly by `SoloTrainingEvaluator`.

It is **not** the ARTCC facility / position / TCP / beacon-code config (that is `ArtccConfigService` /
`NavigationDatabase`), and it is **not** general airspace classification. Only **Class B and Class C** are
parsed — `ParseFeature` returns `null` for every other `CLASS` value, so Class D/E and airport features in
a source GeoJSON are silently dropped (see Footguns). All file references below are
`src/Yaat.Sim/Data/Airspace/` unless stated otherwise.

## Data model

Small types in `Data/Airspace/`, with points as the shared `LatLon` (`Yaat.Sim/LatLon.cs`, `readonly record struct (double Lat, double Lon)` — note **Lat first**):

| Type | File | Shape |
|---|---|---|
| `AirspaceVolume` | `AirspaceVolume.cs` | `Id`, `Ident`, `IcaoId`, `Name`, `Class`, `LowerFtMsl`, `UpperFtMsl`, `Rings` (all `required init`). Owns the containment geometry. |
| `AirspaceClass` | `AirspaceClass.cs` | `enum { Bravo, Charlie }` — **two values only**. |
| `AirspaceBoundaryCrossing` | `AirspaceBoundaryCrossing.cs` | Result of a projected-entry query: `Volume`, `Intersection`, `DistanceNm`, `LookaheadSeconds`, `TimeToEntrySeconds`, `EntryAltitudeFtMsl`. |
| `AirspaceDatabase` | `AirspaceDatabase.cs` | `IReadOnlyList<AirspaceVolume> Volumes` + the lazy `Default` singleton + all loading/parsing/query methods. |

`Rings` is `IReadOnlyList<IReadOnlyList<LatLon>>` — one volume can carry several rings (multiple
disjoint polygons, e.g. the surface area plus the shelf rings of a Class C). All rings are treated as
**positive** (see the doughnut footgun).

## Fixture loading & discovery

`AirspaceDatabase.Default` is a process-wide `Lazy<AirspaceDatabase>` populated by
`LoadDefault()` on first access. `LoadDefault` runs a **3-tier file search** for `*.geojson` and `*.geojson.br`:

1. `AppContext.BaseDirectory/Data/Airspace` (the content-copied fixture next to the built assembly).
2. `AppContext.BaseDirectory` itself (bare build output).
3. `FindFixturesFromWorkingTree()` — walk **up** from `Directory.GetCurrentDirectory()` looking for
   `src/Yaat.Sim/Data/Airspace`, for the source-tree / wrong-cwd case.

If all three tiers come up empty it logs a warning (`"No FAA airspace fixtures found under {Path}"`) and
returns an **empty database** — every downstream airspace query then silently no-ops (see Footguns).

`FromGeoJsonFiles` reads the matched files in case-insensitive sorted order and **dedups by volume `Id`**
across files via `volumesById.TryAdd` (first file wins on a collision). `ReadGeoJsonText` auto-detects
compression by extension: a `.br` path is decompressed through a `BrotliStream`; anything else is read as
plain UTF-8. The shipped fixture is Brotli.

### The fixture and its refresh script

The repo ships one fixture: `Data/Airspace/faa-training-primary-class-bc.geojson.br` (~6.1 MB Brotli). It is
regenerated by `tools/refresh-faa-airspace.ps1`, which:

- Resolves the primary airports of the YAAT training scenarios across 20 default ARTCCs (`ZAB … ZTL`) via
  the vNAS training API (`scenario-summaries/by-artcc/{artcc}` → each scenario's `primaryAirportId`),
  normalizing K-/P-prefixed idents down to the bare 3-letter form.
- Queries the FAA ArcGIS `Class_Airspace` FeatureServer for `CLASS in ('B','C')` and `IDENT in (...)` for
  those airports (in chunks of 30 idents), keyed by `OBJECTID`.
- Writes the merged `FeatureCollection` to the `-Output` path, Brotli-compressing when the path ends in `.br`.

The script defaults to Classes `B` and `C` only — consistent with `ParseFeature` dropping everything else,
the parser would discard any other class even if the fixture carried it.

## GeoJSON parsing

`FromGeoJson` parses the top-level `FeatureCollection`, calling `ParseFeature` per feature. `ParseFeature`:

- Maps `properties.CLASS`: `"B" → Bravo`, `"C" → Charlie`, anything else → `null` (feature dropped).
- Builds `Id` as `FAA-AIS-{OBJECTID}` when `OBJECTID > 0`, else a composite `"{Ident}-{Name}-{lower}-{upper}"`.
- Reads `IDENT`, `ICAO_ID`, `NAME` (falling back to `IDENT`).
- Resolves the altitude band via `ResolveAltitudeFt(props, "LOWER", 0)` and `ResolveAltitudeFt(props, "UPPER", int.MaxValue)`.

`AirspaceDatabase.ResolveAltitudeFt` reads the `{PREFIX}_CODE` / `{PREFIX}_VAL` property pair:
`_CODE == "SFC"` → `0`; a missing value or a sentinel `<= -9990` → the supplied default
(`0` for LOWER, `int.MaxValue` for UPPER); otherwise `round(_VAL)`.

`ParseRings` flattens geometry: `Polygon` coordinates go straight to `ParsePolygon`; `MultiPolygon`
coordinates are iterated polygon-by-polygon into the same flat ring list. `ParsePolygon` reads each
coordinate pair as **`[lon, lat]`** — it stores `new LatLon(pair[1] /* Lat */, pair[0] /* Lon */)`.
Rings with fewer than 4 points are discarded. A feature whose rings all drop out yields no volume.

## Containment geometry

`AirspaceVolume.Contains(position, altitudeFtMsl)` is `ContainsAltitude && ContainsLateral`:

- `ContainsAltitude(alt)` = `alt >= LowerFtMsl && alt <= UpperFtMsl` (inclusive both ends).
- `ContainsLateral(position)` = `PointInRing` true for **any** ring (rings OR-combine).

`PointInRing` (`AirspaceVolume.cs`) is a standard even-odd ray-cast in `(Lat, Lon)` space, returning
`false` for any ring with fewer than 3 points. `FindLateralIntersections(from, to)` walks each ring's edges
and calls `GeoMath.SegmentsIntersect(from, to, a, b, excludeEndpoints: false)`, yielding each hit point —
this is the lateral-crossing input to projected-entry detection.

**Bounding-box pre-filter (hot path).** Each `AirspaceVolume` caches its rings' axis-aligned `(Lat, Lon)`
bounding box (computed once when `Rings` is assigned). `ContainsLateral` and `FindLateralIntersections`
reject in O(1) when the point / segment lies entirely outside that box *before* walking any ring vertices.
The box is a superset of the polygon in the same planar space as the exact test, so results are identical —
it only skips provably-outside work. This matters because `Default` is the **national** Class B/C set (≈500
volumes / ≈665k vertices) and the solo-training per-tick paths (`FindFirstProjectedEntry` per VFR aircraft,
`FindContaining` per aircraft pair) sweep every volume; without the bbox reject each sweep is a six-figure
point-in-polygon walk. Never iterate `Volumes` with a raw `PointInRing`/segment test in a per-tick loop —
go through `Contains` / `FindLateralIntersections` so the pre-filter applies.

## Projected-entry detection — `FindFirstProjectedEntry`

`FindFirstProjectedEntry(aircraft, lookaheadSeconds)` returns the **earliest**
boundary crossing along the aircraft's projected straight-line track, or `null`. It projects the endpoint
position (`ProjectPosition`) and altitude (`ProjectAltitude`) for the full lookahead, then for each volume
considers **three candidate modes** and keeps the one with the smallest `TimeToEntrySeconds`:

1. **Already-inside-at-projected-point** — if `volume.Contains(to, projectedAltitude)`, consider `to` at the
   full lookahead time.
2. **Lateral ring intersection** — for each `FindLateralIntersections(from, to)` hit, time-to-entry is
   proportional to along-track distance (`clamp(distanceNm / lookaheadNm, 0, 1) * lookaheadSeconds`); the
   altitude *at* that time is re-projected and the candidate is taken only if `ContainsAltitude` holds there.
3. **Vertical floor/ceiling crossing** — `ConsiderVerticalEntry` for both `LowerFtMsl` and `UpperFtMsl`:
   requires `|VerticalSpeed| >= 1` fpm, computes `timeToEntry = |Δalt / vs| * 60` (min → s), rejects if outside
   `[0, lookaheadSeconds]`, projects the lateral position at that time, and requires it to be laterally inside.

**Skip-if-already-inside guard:** before any of the three modes, the loop `continue`s on any volume the
aircraft is *already* in (`volume.Contains(from, aircraft.Altitude)`). So this method only ever reports the
**first entry** of a not-yet-entered volume — never re-entry, never exit. Use `FindContaining` for plain
"am I inside" questions (see Footguns).

### Trajectory math — `ProjectPosition` / `ProjectAltitude` / `ResolveAltitudeGoal`

`ProjectPosition` advances along `TrueTrack` by `max(GroundSpeed, 0) * lookahead / 3600` NM via
`GeoMath.ProjectPoint`. `ProjectAltitude` advances by `VerticalSpeed * lookahead / 60`, then **clamps toward
the altitude goal** from `ResolveAltitudeGoal` so a climbing/descending aircraft does not overshoot its
target/floor/ceiling. `ResolveAltitudeGoal` (private, in `AirspaceDatabase`) folds
`Targets.TargetAltitude` together with `AltitudeFloor`/`AltitudeCeiling`.

This is one of two `ResolveAltitudeGoal` implementations — the other is inside `FlightPhysics.UpdateAltitude`
(with `AltitudeSnapFt` hysteresis). They intentionally differ (projection wants the raw trajectory, physics
wants snap hysteresis) but must stay in sync on floor/ceiling resolution. The physics-side integration math
(airspeed frames, altitude snap, performance constants) is owned by [flight-physics.md](flight-physics.md);
this doc does not re-derive it. This is also flagged in
[solo-training-pilot-speech.md](solo-training-pilot-speech.md) (Pitfalls).

## Consumer 1: VFR boundary respect (the hold)

`PilotProactive.TickAirspaceBoundaryRespect(aircraft, scenario, airspace, airportLookup)`
models AIM §3-2-1.4 pilot responsibility: a VFR student must
meet Class B/C entry requirements before crossing the boundary. It early-returns unless **all** of:

- `scenario.SoloTrainingMode` is on,
- the aircraft is **airborne and VFR** (`!IsOnGround && FlightPlan.IsVfr`),
- there is **no active phase** (`aircraft.Phases is { IsComplete: false }` goes to the in-phase step, below).

Then it calls `airspace.FindFirstProjectedEntry(aircraft, lookaheadSeconds: 60)`. If a crossing is found and
`EntryGateSatisfied` is **false** for that volume's class, it installs a fresh single-phase `PhaseList`
holding an `AirspaceBoundaryHoldPhase` configured from the volume (class, ident/icao, name, reference
position via `airportLookup`, volume id, orbit direction, lower/upper band, mode + level-off ceiling).

### Hold modes — turn or level off

The manoeuvre depends on the geometry, not on the airspace class (`AirspaceHoldMode`):

| Mode | Selected when | What it does |
|---|---|---|
| `Orbit` | the aircraft is laterally **outside** the volume's footprint — a ring crossing lies ahead | clears the nav route and turns 180° away from the boundary each tick, capped to `AircraftPerformance.HoldingSpeed(...)` |
| `LevelOff` | the aircraft is already laterally **inside** the footprint — only the climb can enter | sets `ControlTargets.AltitudeCeiling` beneath the floor and leaves course, route and speed alone |

Turning is useless when the shelf is directly overhead, and flying under a Class B shelf is ordinary VFR
practice (AIM §3-2-3.d.2.c); the reported failure (#308) was a KOAK 28R departure orbiting *inside* the
2,100 ft SFO Bravo shelf because the hold never capped the climb.

`AirspaceAvoidance` (`src/Yaat.Sim/Data/Airspace/AirspaceAvoidance.cs`) owns both geometry decisions:

- `LevelOffCeilingFt(volumeFloorFtMsl, magneticCourseDeg, surfaceElevationFt)` — the highest **round hundred
  strictly below** the floor (2,100 → 2,000). The charted floor is inclusive and Mode C is quantized to
  100 ft with up to 125 ft of legal error (14 CFR 91.217(a)(3)), so floor-minus-one would paint as an
  airspace bust. Above `HemisphericAltitude.AglFloorFt` (3,000 AGL) the level drops to the highest
  conforming 14 CFR 91.159 altitude. Returns null when less than `MinimumFlyableAglFt` (1,000 ft, per
  14 CFR 91.119 over congested areas) remains — a surface area — and the caller falls back to `Orbit`.
- `AwayFrom(track, position, boundaryPoint)` — the turn that puts the boundary behind the wing. The orbit
  direction used to be hardcoded right, which drove the aircraft *into* the airspace half the time.

`AirspaceBoundaryHoldPhase` (`src/Yaat.Sim/Phases/AirspaceBoundaryHoldPhase.cs`) overrides
`ManagesSpeed` to `true` **only in `Orbit` mode** — an aircraft levelling under a shelf keeps cruise speed,
so an ATC speed assignment still takes effect. `OnStart` snapshots the pre-hold
route/heading/turn/speed/target-altitude/ceiling. The hold is **silent** — it does not broadcast a pilot
self-report (Issue #154) — with one exception: if the controller has **assigned** an altitude at or above
the volume's floor, `PilotProactive.AnnounceUnableAssignedAltitude` queues
`PilotResponder.BuildUnableAirspaceAltitude` ("unable 3500, that'd put us in the bravo — we can do 2000").
AIM §5-5-6.a.3 requires a VFR pilot to advise ATC rather than fly a clearance that would violate the CFRs,
and 7110.65 §7-9-2 NOTE 1 tells controllers to expect that call. An altitude the *pilot* chose draws
nothing.

`OnTick` completes (returns `true`) when:

| Mode | Exit conditions |
|---|---|
| both | `GateSatisfied` (Bravo clearance / two-way for Charlie) |
| `Orbit` | the controller assigned a heading or added a nav route (they have taken responsibility — otherwise the orbit overwrites the vector every tick and the aircraft circles forever), or `HeldVolumeCanStillBeEntered` goes false. Not under `RMOB` for this Class B while the new track still enters it (`VectorEntersRemainOutsideBravo`): the pilot holds through the vector (`HoldThroughVector`) |
| `LevelOff` | `AltitudeCeiling` no longer matches the phase's own cap (a controller altitude command nulls it), or the aircraft is laterally clear of the footprint now and 60 s ahead |

The `LevelOff` exit deliberately does **not** re-run `FindFirstProjectedEntry`: `ProjectAltitude` honours
`AltitudeCeiling`, so the cap the phase just imposed is what stops the projection. Asking that question
would end the hold on the first tick, restore the climb, and re-trigger the hold — a level/climb
oscillation at tick rate. The ceiling is likewise set **once** in `OnStart` and never re-asserted, so a
controller altitude command cleanly takes over.

On completion `OnEnd` in `Orbit` mode **restores the original route/heading only if the controller has not
since assigned an explicit magnetic heading and has not added a new navigation route** (a non-empty
`NavigationRoute` at `OnEnd` means a `DCT`/direct command was issued during the hold, which must survive
the release), except that a hold that held through a vector under `RMOB` resumes the assigned heading (`ResumeAssignedHeading`) and flies a held-through direct from the route it stashed, and restores the original speed only if there is no explicit speed command. In `LevelOff`
mode it lifts its own ceiling (leaving a controller-issued "maintain VFR at or below" in place) and puts
back the pre-hold `TargetAltitude` — `FlightPhysics.UpdateAltitude` nulls that field when the aircraft
captures the capped goal, so without the restore the climb never resumes. A Class B level-off that ends
Skipped (the phase list was replaced or cleared) instead hands its standing cap, saved ceiling and target to
`AircraftState.BravoCap` in the same step, so the ceiling never loses its owner (see "In-phase Class B cap" below). `CanAcceptCommand` returns
`Allowed` for every command (the hold never rejects controller input). See [phases.md](phases.md) for the
phase lifecycle, `ManagesSpeed` contagion, and the snapshot contract. The feature shipped as pilot-AI milestone M10.1.5
(`docs/plans/pilot-ai-self-training/README.md`); its subplan is deleted, so git history holds the milestone record.

**A paired hold** (an `Orbit` hold standing in front of a held pattern or approach phase, [phases.md](phases.md) "A boundary hold in front of a running phase") follows the free-flight vector rule, and `PhaseRunner.EndHold` ends it. A new heading or direct that keeps the aircraft outside the Bravo ends the orbit and is flown; one into the Bravo is held through (`HeldThroughVector`) and flown once cleared. A heading standing when the hold went in is not new (`HeadingStandingAtStartDeg`) until the first new heading, after which every heading is judged. At the end the held phase's route and heading come back only when no new heading or direct arrived: a held-through direct is put back (`StashedDirect`), and a new heading clears the orbit's turn direction. Only `InitialClimbPhase` and `DepartureProcedurePhase` accept a heading or direct while held without clearing themselves.

**Putting a paired hold in** is the in-phase step of `TickAirspaceBoundaryRespect` (`TickInPhaseBoundaryHold`; the gates, the orbit-first rule, the owed advisory, the Class B request and the below-400 ft "unable to hold, continuing." are in [phases.md](phases.md) "What puts a hold in"). Unlike the free-flight hold it is not silent: the pilot says "that'll take us into the bravo; we'll orbit left here, request bravo clearance." the first second it can speak to the student, and that request is the one `CLBRV`, `RMOB` and the tracker's re-ask answer. A paired orbit levels at the present altitude, never descends, and gives the held phase its altitude target and rate back at its end unless a controller altitude command came during it ([phases.md](phases.md) "A paired orbit never descends").

**Path lookahead and self-release.** In the in-phase step the test is the path the running phase will fly, not the straight ray. `BravoPathPredictor` (`Pilot/BravoPathPredictor.cs`) walks the phase's legs (pattern waypoints, or the navigation route then the final approach course) for 60 s: turns as arcs at the category or phase turn rate, a fly-by lead at each fix, the vertical at the present rate to the planned altitude. Any sample inside a Bravo volume whose band holds the altitude there is an entry, so the hold goes in at the boundary when a turn ahead brings the path in. The altitude of the resumed leg has one source (`PlannedLegAltitudeFt`): a CM given during the hold, else a carried CM, else the departure climb target (upwind, crosswind), else pattern altitude (crosswind keeps a standing target that starts above it); the walk descends at the slower of the category and pattern descent rates and climbs at the larger of the type's initial and category climb rates. A phase with no path source (`HasPathSource`) keeps the straight ray.

A paired hold **self-releases**, uncleared, once `PredictResume` (600 s of the held phase's path through the resume the hold would install) keeps clear of the held Bravo by one orbit radius: the category turn rate at present ground speed, floor 0.15 nm (`TurnMarginNm`). It never self-releases while holding through a vector (`HeldThroughVector`), for a teardrop or for a phase with no path source. A re-hold within 30 s of a self-release logs a warning. In an RPO session nothing holds: `PilotProactive.TickRpoPathWarning` gives the instructor one warning per encounter, "{callsign}: {phase} path enters the {area} Class B uncleared in {n} s (RPO session: no hold)", with no radio call; `AircraftState.InPhaseWarnedArea` holds the warned Class B until the entry is no longer seen, a clearance, or leaving the scope.

### In-phase Class B cap

The boundary hold above runs only in free flight. While a phase runs, an uncleared VFR pilot still may not climb into a Class B (14 CFR 91.131; AIM 3-2-3.b), so `PilotProactive.TickBravoCap(aircraft, scenario, airspace)` keeps a cap beneath the shelf: `AircraftState.BravoCap` (a `BravoCap` record: area name, shelf volume id, `CapFtMsl`, prior ceiling, prior target altitude), the one owner of the `Targets.AltitudeCeiling` it writes (`min(prior ceiling, cap)`). It is a pilot self-restriction, never a controller bound: `AircraftState.ControllerAltitudeCeiling` reads past it (the VFR bound test in `ApproachCommandHandler` and the scenario exporter's `CM B` preset use that, not `Targets.AltitudeCeiling`).

**Solo training only.** In an RPO session nothing starts a cap and every command flies as given; a cap left standing when the session stops being solo is released on its next step (`SimulationEngine.TickPilotProactive` calls `TickBravoCap` in the solo block, ahead of `TickAirspaceBoundaryRespect`, and again for an aircraft that still holds a cap outside it).

**Who and where** (`Pilot/BravoCapScope.cs`):

- An airborne VFR aircraft in any running phase (pattern, approach, departure climb, go-around, low approach) except `MilitaryRoutePhase`, `AerialRefuelingAnchorPhase` and `AirspaceBoundaryHoldPhase`, which own the ceiling themselves. Free flight stays with the hold.
- A shelf the aircraft is laterally under with its floor above it (the lowest such floor), else the volume a projected entry within 60 s reaches while the aircraft is still below its floor; an aircraft above the Class B descending into it gets none. A Class B the pilot is cleared into, or is already inside, is never capped.
- A departure from a runway laterally inside a Class B volume whose floor is at or below the field (a surface area) is treated as cleared and never capped (7110.65 §7-9-3.c).
- The cap level is the free-flight level-off's (`ResolveLevelOffCeiling`), but never below a controller-assigned altitude that is itself under the floor. No flyable level beneath (a surface area) means no cap.

**Lifecycle.** A standing cap is lowered (never raised) under a lower shelf of the same Class B ahead (`TryLowerBravoCap`). It is released on a Class B clearance, laterally clear of the Class B now and 60 s ahead, IFR, or on the ground (`BravoCapScope.ReleaseReason`), putting back the prior ceiling and target altitude. A phase change, a list replacement or the end of a hold never ends it, and neither does the lack of a projected entry. Anything else that overwrites the ceiling with a phase's own drops the record, which the next step re-judges. A go-around nulls every altitude restriction in `GoAroundPhase.OnStart`, which re-asserts the cap through `ReassertBravoCap`; the go-around climb and the low approach's climb-out then end at the cap when it is lower than their target (`GoAroundPhase.IsLevelAtCeilingBelowTarget`; AIM 4-4-1.b) rather than hold runway heading for an altitude the pilot may not reach.

**Controller altitude commands.** Every handler that applies one (CM, DM, a VFR altitude restriction, PTAC, force altitude, a CFIX or clearance altitude, a military-route altitude, a takeoff clearance's altitude) calls `AircraftState.NoteControllerAltitudeCommand`, which bumps `ControllerAltitudeCommandCount` and ends the cap without touching the targets. The next step judges the cap afresh with the command's bound as its prior ceiling. A command that would put the pilot at or above the shelf floor (a maintain, or an at-or-above) draws one `PilotResponder.BuildUnableAirspaceAltitude` call per command (AIM 5-5-6.a.3; 7110.65 §7-9-2 NOTE 1): `AirspaceUnableAdvisedCommand` records the command already answered, shared with the free-flight hold's `AnnounceUnableAssignedAltitude`, so a cap released and started again does not advise twice. An at-or-below bound draws nothing, since flying under it complies. The cap, the count and the advised-command are snapshot-serialized as optional fields ([snapshots-and-replay.md](snapshots-and-replay.md)).

### Speed under a shelf — 14 CFR 91.117(c)

`AirspaceDatabase.IsUnderClassBShelf(position, altitudeFtMsl)` is true when the aircraft is laterally inside
a Class B footprint but below its floor. `FlightPhysics.RegulatorySpeedLimit` reads it on every speed update
and caps indicated airspeed at **200 kt** there instead of the ordinary 250 below 10,000 ft (which a descent to a lower cleared altitude reaches early, see `docs/flight-physics.md`). The lookup
walks a Bravo-only pre-filtered list, and each volume rejects a far-away point on its bounding box first.
`AircraftPerformance.IsSpeedLimitWaived` (14 CFR 91.117(d)) lets an aircraft whose minimum safe speed is
higher fly that speed instead (`max(cap, MinimumSafeSpeedKts)`), and the military-route waiver of 91.117(a)
does not reach the shelf. An assigned speed above the cap stays standing while the aircraft flies 200 and is
taken back up once it leaves the shelf; an aircraft with no speed target that comes under a shelf faster
than 200 slows to it on its own (AIM 4-4-12.j, 4-4-12.k NOTE) — see
[flight-physics.md](flight-physics.md#speed-integration-updatespeed--look-ahead-planning).

### Entry gates

`EntryGateSatisfied` (in `PilotProactive`) and the identical `GateSatisfied` (in the hold phase) read
boolean gate flags on `AircraftState`:

| Class | Gate condition | Backing field(s) |
|---|---|---|
| `Bravo` | cleared into **this** Class B: an explicit `CLBRV` or (solo) an implicit clearance, see below | `AircraftState.IsClearedIntoBravo(ident)`, reading `ClearedBravoIdent`; never satisfied while `IsRemainOutsideBravo(ident)` |
| `Charlie` | two-way comms established | `HasMadeInitialContact && HasControllerAcknowledgedInitialContact` |
| _other_ | `true` (no gate) | — |

These fields live on `AircraftState` (`ClearedBravoIdent`, `RemainOutsideBravo`, `HasControllerAcknowledgedInitialContact`,
`HasMadeInitialContact`) and are snapshot-serialized so replays preserve gate state.

### Solo Class B request and implicit clearance

Solo training only for the implicit grant and the request (RPO and Class C unchanged), `src/Yaat.Sim/Pilot/ImplicitBravoClearance.cs` + `PilotProactive.TryRequestBravoClearance`.

**The clearance is per Class B.** `AircraftState.ClearedBravoIdent` holds the cleared Class B's area name (`AirspaceDatabase.ClassBAreaName`: the volume's Ident, else its ICAO id; every shelf of one Class B shares it, and `ClassBAreas` / `ClassBArea` group them), and `IsClearedIntoBravo(ident)` is true only for that name. It never carries to another Class B: a pilot cleared into one still asks for a different one ahead. `GrantBravoClearance` sets it and resets the entry and exit state, `EndBravoClearance` clears it.

- **Request.** When the first **lateral** Class B entry within 120 s (`FindFirstProjectedEntry` filtered to Bravo, so an earlier Charlie/Delta entry does not hide it) is into a Class B the aircraft is not cleared into, the pilot calls `request clearance into the bravo.` (destination inside that Class B at the surface) or `…through the bravo.`, recorded as a `PilotPendingRequestKind.AirspaceEntry` request that `PilotRequestTracker` repeats every 120 s (150 s after STBY/ROGER). The request keeps its wording in `PilotPendingRequest.BravoWording`. A VFR pilot's airborne check-in to approach or center that asks for a "Bravo transition" (its track enters a Class B within 300 s, `PilotResponder.CheckInBravoEntry`) is recorded at check-in as that Class B's `AirspaceEntry` request (`PilotProactive.RecordVfrCheckIn`), so the pilot does not ask for the same Class B again; a check-in landing at or inside the Class B asks for flight following instead and records none.
- **Repeat at the boundary.** While the pilot waits in the boundary hold of the Class B it asked for, `PilotRequestTracker` rewrites the re-ask (`PilotResponder.BuildBravoBoundaryReask`) to say where it waits: `{callsign}, orbiting outside the bravo, still request clearance {into|through} the bravo.` in `Orbit` mode, `{callsign}, level {altitude} below the bravo, still request clearance {into|through} the bravo.` in `LevelOff` mode. Away from the hold the re-ask is the request as first worded.
- **Explicit clearance.** `CLBRV` (`ImplicitBravoClearance.GrantExplicit`) clears the Class B `ResolveCleared` picks: the one the pilot waits on (`CaptureWait`), else the one it is laterally inside, else the first projected entry within 120 s, else nothing changes.

  Gated on initial contact, not having been tuned away from the student (`AircraftState.IsTunedAwayFrom`), an empty transmission queue and no other open request. A climb into a shelf from below stays silent (issue #154).
- **Implicit clearance.**

  In solo a heading/turn, DCT, pattern entry, MLT/MRT or approach clearance is a Bravo clearance (7110.65 §7-9-2 NOTE 1 says otherwise for real ops; deliberate sim convenience) when the pilot is waiting (open Bravo request or active Bravo hold, captured before dispatch in `ActionArms.Aviation`) and — for a heading/DCT — its level ray enters the waited-on Bravo within 300 s (pattern/approach grant unconditionally while waiting).

  It is also one when, not waiting, a heading/DCT ray enters a Class B it is not cleared into within 120 s, or when a pattern entry/approach clearance is for an airport inside a Class B. The grant names the Class B entered, the airport's, or the waited-on one.

  Only the immediately applied part of a compound grants (`AT …` and later `;` blocks do not). The readback gains `, cleared into the bravo` (`, cleared through the bravo` when the open request asked to go through). With the clearance held for that Class B, the boundary hold's gate is satisfied, so a vector no longer ends the orbit only for the next second to re-arm it.
- **Remain outside.** `RMOB [minutes]` (7110.65 §7-9-2.a, minutes 1 to 60) is `ImplicitBravoClearance.ApplyRemainOutside`. `ResolveRemainOutside` picks the Class B: the one the pilot waits on, else one it already remains outside, else `ResolveCleared`'s, else the nearest within `RemainOutsideReachNm` (30 NM); none means the pilot says "say again, we're not near the bravo" and nothing changes.

  Inside it in 3D (so a pilot levelled under a shelf is outside) the pilot says "we're inside the bravo, say intentions", keeps its clearance and sets nothing. Otherwise `AircraftState.StartRemainOutsideBravo` ends any clearance for that Class B and stores `RemainOutsideBravo` (area name, minutes, ask schedule; snapshot-serialized), read through `IsRemainOutsideBravo(ident)`.

  While it stands, no implicit grant (`TryGrant`) reaches that Class B and the pilot raises no request of its own for it. Landing, leaving the area and `TickBravoClearanceExpiry` leave it alone; an explicit `CLBRV` (`GrantBravoClearance`) ends it, and a frequency change keeps it (AIM 4-4-10.a).

  The pilot reads back "remain outside the bravo" (with minutes: "expect clearance in one five minutes", digit by digit). An open airspace-entry request for that Class B closes as Denied, ending its repeats (`PilotRequestTracker.ResolveResponse`).

  When the pilot was waiting on that Class B, `PilotProactive.TickRemainOutsideBravoAsk` has it ask once "{callsign}, any estimate on the bravo?" at `RemainOutsideAskSeconds` (300 s) after the instruction, or at the minutes plus `RemainOutsideAskAfterExpectSeconds` (60 s), recorded as an `AirspaceEntry` request that repeats once if unanswered; a spent ask closes silently, a second `RMOB` denies it, `STBY` leaves the pilot holding (7110.65 §2-1-18.d), a frequency change cancels a pending ask, and an `RMOB` with no waiting pilot schedules none.

  A vector or direct into that Class B is read back in the compound's order with the advisory in its place (`PilotResponder.AppliedCompound.NotClearedIntoBravo`, `ImplicitBravoClearance.FindRemainOutsideConflict`): "heading zero niner zero takes us into the bravo, we're not cleared" (§7-9-2 NOTE 1); such a command grants nothing and does not answer the open ask, and the boundary hold keeps the pilot outside until `CLBRV`, then the stored heading or direct is flown.
- **Ending.** A full-stop landing ends it (`LandingPhase` and `HelicopterLandingPhase` touchdown call `EndBravoClearance`; 7110.65 §7-9-3.b, AIM §3-2-3.d.2.b). Otherwise `PilotProactive.TickBravoClearanceExpiry` runs each tick on airborne aircraft. Laterally inside any volume of the cleared Class B, at any altitude, it marks the Class B entered (`HasEnteredClearedBravo`). Before that first entry nothing ends the clearance, so one given while turning or minutes out is kept until used. After entry it ends once the aircraft has been laterally outside every volume, with no re-entry into that Class B projected within 120 s (`FindFirstProjectedEntry` over `ImplicitBravoClearance.VolumesOf`), for `ImplicitBravoClearance.ExitGraceSeconds` (120 s) in a row. `BravoExitSinceSeconds` stamps the start of the outside stretch, and a re-entry or a projected entry resets it. A touch-and-go, a frequency change and a vertical exit under a shelf keep the clearance.

`HasControllerAcknowledgedInitialContact` is set whenever the student issues a successful command
(`RoomEngine.SendCommandAsync`, mirrored in `SimulationEngine.SendCommand`). `HasMadeInitialContact` is
normally set by the AI pilot's proactive check-in, but that check-in is suppressed when the pilot cannot
initiate contact with the student (`PilotInitialContactEligibility.CanInitiateWithStudent` — track owned by
another position with no handoff inbound, e.g. an S2 tower scenario whose arrivals stay with approach). In
that case the AI pilot would never speak first, so a student command also marks `HasMadeInitialContact`:
both call sites route through `PilotInitialContactEligibility.RegisterControllerContact(aircraft, scenario)`,
which sets the pilot side only when `CanInitiateWithStudent` is false. This is what lets the Charlie gate
clear when a tower student directs an approach-owned VFR arrival into the Class C.

## Consumer 2: separation-minima selection

`SoloTrainingEvaluator.ResolveRequirement(a, b, airspace, lookaheadSeconds)`
(`src/Yaat.Sim/Training/SoloTrainingEvaluator.cs`) picks which separation standard a pair must meet. The
airspace database drives the VFR-involved branches:

- **Both IFR** → IFR radar separation (3 NM / 1,000 ft), no airspace lookup.
- **A volume contains either aircraft (projected)** via `FindApplicableAirspaceClasses` →
  `FindContainingProjectedAirspace` → `airspace.FindContaining(projectedPosition, projectedAltitude)`:
  - **Class B present** → `IsLargeOrTurbojet(a) || IsLargeOrTurbojet(b)` selects between **1.5 NM / 500 ft**
    (large >19,000 lb or turbojet, §7-9-4) and **target-resolution / 500 ft** (light, §7-9-4).
  - **Class C present, or the synthetic outer-area applies, and the pair is mixed IFR/VFR** →
    Class C target-resolution / 500 ft (§7-8-2/3, AIM §3-2-4).

Note that `SoloTrainingEvaluator` has its **own private** `ProjectPosition`/`ProjectAltitude`
(in `SoloTrainingEvaluator.cs`) — they are *not* the `AirspaceDatabase` ones, and `ProjectAltitude` here
does no goal clamping. See [solo-training-evaluation.md](solo-training-evaluation.md) (the Separation criteria
section) for how these requirements feed the scorer and the per-tick `Evaluate` entry point.

### The synthetic Class C outer area

The Class C "outer area" (the 20 NM ring used to extend §7-8 separation responsibility) is **not a polygon in
the GeoJSON**. `SoloTrainingEvaluator.IsInClassCOuterArea` groups the Charlie volumes by airport id
(`IcaoId` else `Ident`), looks the airport fix up in `NavigationDatabase` trying both the raw id and a
`"K"`-prefixed variant, takes the group's max `UpperFtMsl` as the ceiling, and returns true when the projected
position is within a **hardcoded 20.0 NM radius** and at-or-below that ceiling. If the airport fix is missing
from navdata, the outer-area check silently returns `false`.

## Tick-loop wiring (cross-repo)

`TickAirspaceBoundaryRespect` and `TickBravoCap` are called once per aircraft in **PostPhysics** from `SimulationEngine.TickPilotProactive` (`src/Yaat.Sim/Simulation/SimulationEngine.Tick.cs`), with `AirspaceDatabase.Default`; yaat-server rooms run the same step through `RoomEngine.ProcessPostPhysics` (`RunPostPhysics`), so a proactive airspace tick added there needs no server-side wiring of its own. ## Footguns & gotchas

- **Only Class B and C are parsed.** `ParseFeature` returns `null` for any other `CLASS`, so Class D/E and
  airport features in a source GeoJSON are silently dropped. The boundary-hold and separation logic never
  fire for Class D even though the gate switches carry a permissive `_ => true` default.
- **The entry-gate switch is duplicated in (effectively) three places:** `AirspaceBoundaryHoldPhase.GateSatisfied`,
  `PilotProactive.EntryGateSatisfied`, and the implicit class checks in `SoloTrainingEvaluator.ResolveRequirement`.
  Add a class or change a gate rule and you must touch all of them — the compiler will not catch a missed one
  because the phase/proactive switches fall through to `_ => true`.
- **Two `ResolveAltitudeGoal` implementations.** `AirspaceDatabase.ProjectAltitude` (no snap hysteresis,
  projection wants raw trajectory) vs `FlightPhysics.UpdateAltitude` (with `AltitudeSnapFt`). They must stay in
  sync on floor/ceiling resolution. Also flagged in [solo-training-pilot-speech.md](solo-training-pilot-speech.md).
- **The Class C outer area is synthetic.** It is a hardcoded 20 NM radius around the navdata airport fix, not a
  polygon. If the airport fix is absent from `NavigationDatabase` (raw or `K`-prefixed), the check returns
  `false` and the extended separation responsibility silently does not apply.
- **Empty-DB silent no-op.** When fixture discovery finds nothing, `LoadDefault` logs a warning and returns
  `new AirspaceDatabase([])`. Every query then returns nothing and all airspace behavior disappears with no
  exception — a wrong cwd or a missing content-copy can disable the whole subsystem invisibly. The
  `FaaTrainingPrimaryFixture_LoadsSfoBravoAndOakCharlie` test (`tests/Yaat.Sim.Tests/AirspaceRespectTests.cs`)
  guards that the fixture actually loads.
- **`AirspaceDatabase.Default` is a process-wide `Lazy` singleton populated from disk** — like other Yaat.Sim
  singletons it can race in parallel xUnit if a test reads it mid-population (see the static-singleton-races
  note in `CLAUDE.md`).
- **GeoJSON coordinate order is `[lon, lat]`.** `ParsePolygon` reads `pair[1]` as Lat and `pair[0]` as Lon, and
  `LatLon` stores `(Lat, Lon)`. Swap them and containment flips silently.
- **`FindFirstProjectedEntry` skips any volume the aircraft is already inside.** It reports only the first
  not-yet-entered boundary, never re-entry or exit. Do not repurpose it for "am I inside" — use `FindContaining`.
- **`ParseRings` treats every ring as a positive ring.** `ContainsLateral` OR-combines all rings, so a true
  polygon hole (a doughnut) would be treated as solid. Fine for the current SFO/OAK fixture, but a correctness
  trap if a doughnut-shaped volume is ever added.
- **The airspace ticks live in the shared post-physics step.** `SimulationEngine.RunPostPhysics` runs them with `AirspaceDatabase.Default` for both the bare engine and yaat-server's `RoomEngine`; the separation path in `TickProcessor` is the one server-side call.

## Extending

- **Add Class D** — add `Delta` to the `AirspaceClass` enum, map `"D"` in `ParseFeature`, add the gate rule in
  all three switch sites (hold phase, proactive, evaluator), and re-run `tools/refresh-faa-airspace.ps1` with
  `-Classes B,C,D` so the fixture carries the volumes.
- **Refresh the fixture** — `pwsh tools/refresh-faa-airspace.ps1` (optionally `-Artccs`, `-Idents`, `-Classes`,
  `-Output`). It rediscovers training primary airports and re-queries the FAA ArcGIS service.
- **Add a query** — extend `AirspaceDatabase` with a method over `Volumes`; keep the `[lon, lat]` / `(Lat, Lon)`
  convention and remember the skip-if-already-inside semantics differ from plain containment.
